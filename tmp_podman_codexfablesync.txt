Subject: Re: Review request — IBK3 findings (1 high, 2 medium, 3 low)

Reviewed at tip fb3692b78 (includes 94d1f07b6, which added the range
executor): IndexedBlockWireV3.lean, IndexedBlockWireV3Tests.lean,
docs/20260831-ibk3-paged-dictionary-layout.md, plus
PagedTermDictionary.lean as the embedded component. Nothing modified.

FINDING 1 — HIGH. scanRowPrefixPages silently drops rows; its
docstring says it rejects.
  formal/lean4/L4Factoidal/Storage/IndexedBlockWireV3.lean:203
The scan uses `rows.filterMap (tripleFromPages? ...)`. When a
referenced page is omitted or its range mismatches
(lookupPageBytes?, lines 167-168), or a page decodes but yields a
literal in subject/predicate position (line 188), that ROW is
dropped and the scan returns the remaining triples. The docstring
(lines 190-194) claims "an omitted, mismatched or malformed page
rejects the scan rather than substituting an unrelated term". It
never substitutes — true — but it does not reject: it returns a
smaller answer that looks like a real result. A host that
under-supplies pages gets silently incomplete SPARQL answers. This
is the same failure class your delta work just avoided ("malformed
= hard failure, never a best-effort stale read"). Fix: return
`Option (List Triple)` and use mapM over rows, so any failed term
lookup fails the whole scan. Note the tests only exercise the
all-pages-supplied path (Tests:57-63); there is no guard for a
missing or wrong-range page, so the false claim is untested today.

FINDING 2 — MEDIUM. The range path never checks predicate-locality
and the bound need not pin the predicate.
  IndexedBlockWireV3.lean:145-148, 195-206
decodeRowPrefix? deliberately skips whole-block admission
(documented, fine), but scanRowPrefixPages accepts any
PatternBound. The docstring says "predicate-bound scan"; nothing
enforces bound.p being set, and prefix rows are not checked for one
predicate. With Merkle-verified bytes this is not an integrity
hole, but the API lets a host run an under-constrained scan on a
partial prefix and read the result as block-complete. Either take
the predicate as an explicit argument, or state the host contract
in the docstring: completeness requires rowPrefix == full rows
range, and predicate trust comes from the artifact, not the scan.

FINDING 3 — MEDIUM. encodeList swallows dictionary-encode failure.
  IndexedBlockWireV3.lean:95
`(PagedTermDictionary.encode? block.dict).getD ByteArray.empty`
means an unsupported dictionary yields a framed, CRC-valid artifact
that claims dictionaryBytes=0. decode rejects it downstream, so
there is no wrong-accept, but a well-checksummed garbage artifact
is exactly what a future tool will trip over. V1/V2 share the
encodeList pattern and it exists for corrupt-fixture tests
(Tests:22). Suggest marking encodeList test-only in the module
comment, or making it private and exposing a corrupt-fixture
helper in the tests file.

FINDING 4 — LOW. Zero-row artifacts are unrepresentable, and the
design doc does not say so.
  IndexedBlockWireV3.lean:81-84 (onePredicate), 136-139
  (predicateLocal): both return false for the empty list, so
encode? refuses and decode rejects an empty predicate block.
Probably right — but it means a future compactor that deletes the
last triple of a predicate must remove the artifact and its
manifest entry, never write an empty one. Put that sentence in
docs/20260831-ibk3-paged-dictionary-layout.md before the compactor
exists.

FINDING 5 — LOW. Admission accepts non-canonical PTD1 variants, so
"canonical bytes" is encoder-side only.
  PagedTermDictionary.lean:100-102
decodePrefix accepts any nonzero pageTerms consistent with
pageCount; the encoder always writes 256. Two different byte
strings decode to the same Block, so decode is not injective over
accepted inputs. Harmless under Merkle addressing of the bytes,
but it weakens any dedup/content-addressing claim. Either check
pageTerms == defaultPageTerms at admission, or say in the doc that
canonicality is a property of the encoder, not the acceptor.

FINDING 6 — LOW. Framing constants are correct but hand-tied.
  IndexedBlockWireV3.lean:215
`input.drop 5 |>.take (input.length - 9)` hard-codes
magic+version (5) and 5+CRC (9) next to a prefixBytes constant of
13. Correct today; derive them from named constants so a future
header change cannot silently shear the CRC window. The
end-of-artifact CRC read at line 216 is safe only because of the
length check at line 214 — keep those adjacent if you refactor.

Verified good, for the record: encode? overflow guards (line 104)
on top of V1.supported's fitsU32 admission; exact-length admission
with no trailing bytes (line 221); orderedRows? forcing positions
to be exactly 0..n-1 with duplicates rejected (129-134); page plans
bounded inside dictionaryBytes before absolutizing (163);
tripleFromPages? refusing literal subjects/predicates (186-188);
PTD1 full decode validating per-page boundaries and directory
contiguity (decodePages?, directoryContiguous); and the corrupt-
byte rejection guard in the tests. The denotation claim (terms and
rows mean exactly IndexedBlock.Block, no vocabulary interpretation)
is accurate as written.
