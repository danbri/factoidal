# Using Factoidal from an AI agent

Factoidal is an RDF / SPARQL / Web-data engine whose logic is written
in two formal languages and extracted to executable code:

- **F\* flavour** (`formal/fstar/`): verified F\* source, extracted to
  OCaml, compiled to native binaries (committed in the repo), to
  JavaScript (js_of_ocaml) and to WebAssembly (wasm_of_ocaml) for the
  npm package `@factoidal/core`.
- **Lean 4 flavour** (`formal/lean4/`, library `L4Factoidal`): Lean
  source with kernel-checked proofs (no `sorry`, no user `axiom`),
  compiled via Lean→C→Emscripten into one wasm module
  (`l4factoidal.wasm`, committed), plus native test harnesses built
  with `lake`.

There is no hand-written SPARQL evaluator in either flavour; the code
you run is extracted from the formal source. Standing verification
qualifier (repository policy, quoted exactly): "parser and algebra
spec verified in F\*; on-disk backend has unverified OCaml-side
optimization layers being migrated back to F\* (see
fstar-purity-unwind.md)".

Provenance of every number in this file: F\* scores come from
`docs/test-results/latest.json` (dated 2026-08-24, branch
`claude/main`, regenerated by `./w3c-tests.sh` and nightly CI); Lean
scores were measured 2026-08-25 by running the lake-built harnesses on
this checkout. Every command and code snippet shown was executed
against this checkout before being written down. Scores are always
"N pass, M fail (out of T)"; a cell that could not be demonstrated
says "not verified", never a guess.

## Getting an engine (no toolchain required for three of the four)

### 1. Committed native binaries — F\* flavour

The repository commits the built binaries, so a fresh clone runs with
no F\*/OCaml toolchain:

```
bin/linux-x86_64/     Linux x86-64 (statically linked)
bin/darwin-arm64/     macOS Apple Silicon
```

Each platform directory holds `factoidal` (the CLI: query, serve,
parse/dump, canonicalize, entail, update, shacl, shex, rml, csvw,
jsonld, rif, cottas-import/info, compact, test) and `w3c_runner` plus
per-spec suite runners (`owl_runner`, `rdfc10_runner`, `shacl_runner`,
`shex_runner`, `rml_runner`, `rif_runner`, `csvw_runner`,
`xml_runner`, `xslt_runner`, `schematron_runner`, `mathml_runner`,
`jsonschema_runner`, `jsonld_*_runner`, `vc_runner`, `did_runner`).
`bin/linux-x86_64/factoidal help` prints the full subcommand list.

### 2. npm `@factoidal/core` — F\* flavour for Node and browsers

The npm registry serves `@factoidal/core` 0.1.0 (checked 2026-08-25);
the in-tree package `npm/factoidal/` is 0.2.0 — run from a repository
checkout (`require('<checkout>/npm/factoidal')`) to get the current
surface, including the Lean subpaths below. Subpath map
(`package.json` `exports`):

| Import | Engine |
|---|---|
| `@factoidal/core` | F\* engine, JavaScript build (Node CJS/ESM) |
| `@factoidal/core/wasm` | F\* engine, WebAssembly build, same API |
| `@factoidal/core/browser` | F\* engine for browsers |
| `@factoidal/core/fn` | typed value-in/value-out function surface (chainable `FnDataset`) |
| `@factoidal/core/rdfjs` | RDF/JS data factory |
| `@factoidal/core/l4` | raw Lean wasm loader (`loadL4()` → `eng.call(op, argsJson)`) |
| `@factoidal/core/l4-core` | Lean engine behind the SAME typed API as the root import |

All engines expose `capabilities()`, an object of feature booleans —
call it instead of assuming a feature exists. SELECT results are
`Map<string, Term>` per row: read a binding as
`rows[0].get('o').value`.

### 3. Lean wasm module — Lean flavour, committed

`npm/factoidal-lean/` (package `@factoidal/lean`, 0.1.0 in-tree, NOT
yet on the npm registry — checked 2026-08-25, the registry returns
404) and `docs/web/hub/assets/l4/` both carry the committed artifact:
`l4factoidal.js` (loader), `l4factoidal.mjs` (Emscripten glue),
`l4factoidal.wasm` (~4 MB). Runs in browser, Node ≥20, and Deno.
`@factoidal/core/l4-core` resolves these assets via a three-step
ladder: installed `@factoidal/lean`, then `$FACTOIDAL_L4_ASSETS`, then
the repository checkout.

### 4. Lean native harnesses — require the Lean toolchain

Native Lean binaries other than `l4factoidal` (below) are NOT
committed. To build: `curl -sSf https://elan.lean-lang.org/elan-init.sh
| sh -s -- -y`, then `export PATH="$HOME/.elan/bin:$PATH"`, then
`cd formal/lean4 && lake build` (the build also re-checks every
theorem and `#guard`). Executables land in
`formal/lean4/.lake/build/bin/`: `l4wasm-cli` (the dispatch ABI,
natively), `l4w3c` (W3C manifest runner), and per-spec probes
(`l4rdfc-probe`, `l4jsonld-probe`, `l4owl-probe`, `l4shacl`, `l4shex`,
`l4rml`, `l4rif`, `l4xslt`, `l4xmlconf`, `l4jsonschema`, `l4mathml`,
`l4schematron`, `l4csvw-rdf`, `l4csvw-json`, `l4vc-probe`, …). W3C
test fixtures are git submodules: run `tools/ensure-test-env.sh`
first; with the fixtures absent every suite reports zero tests
discovered and the score means nothing.

### 5. `l4factoidal` — the committed Lean CLI

`bin/linux-x86_64/l4factoidal` is a committed binary (iron rule 9):
it runs from a fresh clone with no Lean toolchain, the same way
`bin/linux-x86_64/factoidal` (F\* flavour) does. It is a real
command-line interface, not the ABI smoke tool — named verbs and
flags over the same `Wasm/Ops/*.lean` functions the wasm build and
`l4wasm-cli` call (`formal/lean4/Wasm/Cli.lean`), so a person or a
script can drive the Lean engine without knowing the dispatch ABI's
JSON envelopes. Verbs: `parse`, `query`, `update`, `canonicalize`,
`closure --regime rdfs|rho-df|rdfs-plus|owl-rl`, `owl-consistent`,
`owl-entails`, `cl parse|serialize|alpha-norm|normalize|finite-sat`
(Common Logic / IKL), `version`,
`ops`. `l4factoidal help` prints the full flag reference. Exit codes:
0 success/true, 1 failure/false/error, 2 usage error.

```
$ bin/linux-x86_64/l4factoidal parse --format turtle --out nquads <<< \
    '@prefix ex: <http://example.org/> . ex:a ex:p ex:b .'
<http://example.org/a> <http://example.org/p> <http://example.org/b> .

$ bin/linux-x86_64/l4factoidal owl-consistent data.nq --fuel 5000
true
```

`l4wasm-cli` (`Wasm/Main.lean`, `call`/`callseq`) is unchanged and
stays the ABI smoke driver `Wasm/native-smoke.sh` pins — build it
from source per §4 above. `l4factoidal`'s own smoke suite is
`Wasm/cli-smoke.sh`.

## Result conventions (both flavours)

- **JSON envelope.** The engine ABIs (F\* npm entry and the Lean
  dispatch) answer every op with one JSON document:
  `{"ok":true, ...fields...}` on success,
  `{"ok":false,"error":"<message>"}` on failure. Errors never cross
  the boundary as exceptions; the JS wrappers convert `ok:false` into
  a thrown `Error`. The dispatch ABI version is `"1"` on both engines.
- **Three-valued OWL verdicts.** `owlIsConsistent` /`owlEntails`
  answer `true`, `false`, or `null`. `null` means the reasoning
  budget ran out, and `reason` names the cap — a budget-out is never
  reported as `false`. Both accept
  `{ fuel: number | string }` to raise the budget.
- **Unknown-op / unimplemented-feature behaviour.** The Lean engine
  entry (`l4-core`) rejects operations the Lean extraction does not
  implement with an engine-capability error rather than silently
  falling back to the F\* engine. Probe `capabilities()` (JS) or the
  `ops` reflection op (dispatch ABI) first.
- **Long runs.** Cap ad-hoc CLI parses and queries with
  `timeout 600 <cmd>`; a run that trips the cap should be re-tried on
  smaller input rather than left hanging.

## Worked examples — F\* CLI

Every command below was run on `bin/linux-x86_64/` (substitute
`darwin-arm64` on macOS). Files are ordinary Turtle/SPARQL text.

```bash
# SPARQL query (ASCII result table on stdout)
bin/linux-x86_64/factoidal query --data data.ttl --query q.rq
# inline query text:
bin/linux-x86_64/factoidal query --data data.ttl -e 'SELECT ?s WHERE { ?s ?p ?o }'

# RDFC-1.0 canonical N-Quads
bin/linux-x86_64/factoidal canonicalize data.ttl

# RDFS or OWL-RL closure, materialized as N-Triples
bin/linux-x86_64/factoidal entail --data data.ttl --regime RDFS

# SPARQL 1.1 Update in memory, dump result
bin/linux-x86_64/factoidal update --data data.ttl -e 'INSERT DATA { <http://e/x> <http://e/p> "v" }'

# SHACL Core validation, JSON verdict
bin/linux-x86_64/factoidal shacl --data data.ttl --shapes shapes.ttl --json
# -> {"conforms":true,"report":"..."}

# JSON-LD -> N-Quads (inline @context only; a remote @context IRI is
# an explicit error: "remote contexts need a loader this CLI does not have")
bin/linux-x86_64/factoidal jsonld --in doc.jsonld

# SPARQL 1.1 Protocol server (tested with an HTTP GET returning
# application/sparql-results+json); add --rw --delta-log for durable update
bin/linux-x86_64/factoidal serve --port 3030 --dataset data.ttl

# COTTAS on-disk storage: summary + query
bin/linux-x86_64/factoidal cottas-info store.cottas
bin/linux-x86_64/factoidal query --data-cottas store.cottas -e 'SELECT ?o WHERE { ?s ?p ?o }'

# W3C suites from the committed runner (full battery ~25 min: `test w3c`)
bin/linux-x86_64/factoidal test rdfc10      # prints "RDFC-1.0 tests: 86 pass, 0 fail, 0 stub (out of 86)"
bin/linux-x86_64/w3c_runner bind            # one named SPARQL suite: "TOTAL: 10 pass, 0 fail, 0 skip, 0 unsupported"
```

Other CLI verbs with the same shape (run `factoidal help` for exact
flags): `dump`, `dump-nq`, `dump-turtle`, `count`,
`graphs list|get|hash|diff`, `shex`, `rml`, `csvw`, `rif`,
`cottas-import`, `compact`.

## Worked examples — F\* npm

From a repository checkout (`const f = require('<checkout>/npm/factoidal')`)
or `npm install @factoidal/core` (0.1.0 surface). All functions return
Promises.

```js
const f = require('@factoidal/core');            // or …/core/wasm for the wasm build

// Parse + query. SELECT rows are Map<string, RDF/JS Term>.
const rows = await f.query('<http://e/a> <http://e/p> "v" .',
  'SELECT ?o WHERE { ?s ?p ?o }', { format: 'ntriples' });
rows[0].get('o').value;                          // -> "v"

// Entailment regime inside query(): 'RDFS' | 'OWL-RL' | 'x-rdfscore' | 'x-rdfsplus'
await f.query(ttl, 'ASK { ex:rex a ex:Animal }', { entail: 'x-rdfscore' }); // -> true

// Update, serialize, canonicalize
const ds2 = await f.update(ttl, 'INSERT DATA { <http://e/b> <http://e/p> "w" }');
await f.serialize(ds2, { format: 'nquads' });
await f.canonicalize(ds2);                       // RDFC-1.0 canonical N-Quads

// OWL 2: RL closure (mode is a positional string); three-valued DL
// verdicts (null = budget-out + reason)
await f.owlClosure(ttl, 'OWL-RL');               // Dataset; also 'RDFS'
await f.coreRdfsClosure(ttl);                    // {ok, ntriples} — certified six-rule rdfs-core closure
await f.rdfsPlusClosure(ttl);                    // {ok, ntriples, rounds}
await f.owlIsConsistent(ttl);                    // {consistent:true|false|null, reason?}
await f.owlEntails(premiseTtl, conclusionTtl);   // {entailed:…, via:'closure'|'refutation'}

// SHACL / ShEx
await f.shaclValidate(dataTtl, shapesTtl);       // {conforms, report}
await f.shexValidate(dataTtl, shexjText, focusIri, shapeIri); // -> true/false

// RML Core (http://w3id.org/rml/ vocabulary; JSONPath refs like "$.name")
await f.rmlMap(mappingTtl, sourceJsonText, 'json');
// CSVW: csv text (+ optional metadata JSON) -> Dataset
await f.csvwToRdf('name,age\nAda,36\n');
// RIF Core saturation over a premise graph
await f.rifEval(dataTtl, rifCoreXml);

// XML stack
await f.xmlWellformed('<a><b/></a>');                          // true
await f.xpathEval('<r><a>1</a><a>2</a></r>', 'count(/r/a)');   // {resultType:'number', value:'2'}
await f.xsltTransform(stylesheetXml, sourceXml);               // result document text
await f.schematronValidate(schematronXml, instanceXml);        // {findings:[...]}
await f.mathmlEval('<math><apply><plus/><cn>2</cn><cn>3</cn></apply></math>');
                                                               // {kind:'rat', num:5, den:1}
await f.xformsRecalc('<data><x>5</x><y>0</y></data>',
  [{ target: 'y', calculate: '/data/x * 2' }]);                // instance + per-node validity
await f.jsonSchemaValidate('{"type":"number"}', '42');         // {valid:true, result:'pass'}

// SPARQL §17.6 extension functions — sync or async JS callable from FILTER/BIND
await f.registerExtensionFunction('http://example.org/fn/double',
  async (args) => Number(args[0].value) * 2);
// (the hub's Wikifunctions demo registers wikifn-fstar compiled functions this way)

// SERVICE against an in-process endpoint registry (probed under LATERAL)
await f.registerServiceEndpoint('https://svc-a.example/sparql', remoteTtl);
await f.query(localTtl, `SELECT ?s ?label WHERE {
  ?s :x :y . LATERAL { SERVICE <https://svc-a.example/sparql> { ?s :label ?label } } }`);

// Storage: COTTAS bytes round-trip and HDT read-only query
const bytes = await f.toCottas(ttl);             // Uint8Array
const h = await f.openCottas(bytes);
await f.queryCottas(h, 'SELECT ?o WHERE { ?s ?p ?o }');
await f.closeCottas(h);
await f.queryHdt(hdtFileBytes, 'SELECT ?s WHERE { ?s ?p ?o }');

// VC / DID
await f.vcSha256Hex('abc');                      // 'ba7816bf…'
await f.didKeyResolve('did:key:z6Mk…');          // DID document as a Dataset
await f.jsonldFromRdf(ttl);                      // expanded JSON-LD node objects
```

JSON-LD inputs must carry inline `@context` values: neither the CLI
nor the npm entry fetches remote contexts, and a remote `@context` IRI
fails with an explicit loader error. The repository keeps an offline,
content-addressed snapshot store of remote contexts under
`third_party/jsonld-context-cache/`
(`tools/jsonld-context-cache.sh resolve <URL>` prints a cached body to
inline; `add <URL>` fetches a new one). The VC checkers vendor the
VCDM v2 base context as data.

## Worked examples — Lean engine (wasm + `l4-core`)

```js
// Same typed API as the root import, answered by the Lean extraction:
const l4 = require('@factoidal/core/l4-core');
const rows = await l4.query('<http://e/a> <http://e/p> "v" .',
  'SELECT ?o WHERE { ?s ?p ?o }', { format: 'ntriples' });
rows[0].get('o').value;                          // -> "v"
await l4.canonicalize('_:b <http://e/p> "v" .'); // -> '_:c14n0 <http://e/p> "v" .'
await l4.rdfsPlusClosure(ttl);                   // {ok, ntriples, rounds}; also coreRdfsClosure, rhoDfClosure
await l4.owlClosure(ttl, 'OWL-RL');              // Dataset — mode is a positional string here too
await l4.owlIsConsistent(ttl);                   // three-valued, same envelope as the F* engine
const caps = await l4.capabilities();            // feature booleans — consult before calling
```

`capabilities()` on the Lean entry (2026-08-25):
parse/query/update/serialize/canonicalize/graphs/canonicalHash/

## The Lean dispatch ABI for non-JS hosts

For a person or a script that wants named verbs and flags instead of
this ABI directly, use `l4factoidal` (§5 above) — it calls the same
op functions this section describes.

The wasm module (and the native `lake exe l4wasm-cli`) serve ONE
entry: `l4_call(op, argsJson) -> resultJson`, where `argsJson` is a
JSON array of strings (positional arguments) and the result is the
`{"ok":…}` envelope. C-level symbols in `l4_shim.c`: `l4_init()`,
`l4_call_c(op, args_json)`, `l4_free_result(ptr)` — strings are
NUL-terminated UTF-8, the returned pointer must be freed exactly once
via `l4_free_result`.

**Enumerate ops with the `ops` reflection op and trust it over any
static list** — the surface grows (op names observed 2026-08-26:
`parseToDatasetJson`, `queryDataset`, `updateDataset`,
`serializeNQuads`, `serializeTurtle`, `canonicalizeToNQuads`,
`owlClosure`, `owlIsConsistent`, `owlEntails`, `rhoDfClosure`,
`rhoDfFragmentCheck`, `rdfsPlusClosure`, `clParse`, `clSerialize`,
`clAlphaNorm`, `clNormalize`, `clFiniteSat`, `ops`, and the
dataset-handle ops
`datasetOpen`, `datasetQuery`, `datasetUpdate`, `datasetSerialize`,
`datasetClose` — 23 in all through the IO entry). ✅ The committed wasm
artifact was rebuilt on 2026-08-26 (sha256 `91fb323e…`) and now matches
its source: `clToDataset` and `queryWithIklService`, deleted by
https://github.com/danbri/factoidal/issues/626, answer `unknown op`,
and the four CL/IKL ops of
https://github.com/danbri/factoidal/issues/623 are present. That
rebuild closed https://github.com/danbri/factoidal/issues/627. The
handle ops are served only through the IO entry
(`l4_call_c` / the CLI); the pure `l4_call` export omits them from its
`ops` answer.

Native driver, same two strings the wasm carries:

```bash
cd formal/lean4
echo '{}' > /tmp/empty.json
.lake/build/bin/l4wasm-cli call ops /tmp/empty.json
# {"ok":true,"abiVersion":"1","ops":[…]}

printf '%s' '["<http://e/a> <http://e/p> \"v\" .", "SELECT ?o WHERE { ?s ?p ?o }"]' > /tmp/q.json
.lake/build/bin/l4wasm-cli call queryDataset /tmp/q.json
# {"ok":true,"kind":"select","srj":{"head":{"vars":["o"]},"results":{"bindings":[{"o":{"type":"literal","value":"v"}}]}}}
```

Dataset handles avoid re-parsing across calls; handle state lives for
one process, so batch with `callseq` (a JSON array of
`[op, [arg, …]]`):

```json
[ ["datasetOpen",      ["<http://e/a> <http://e/p> \"v\" .", "ntriples", ""]],
  ["datasetUpdate",    ["h1", "INSERT DATA { <http://e/b> <http://e/p> \"w\" }"]],
  ["datasetQuery",     ["h1", "SELECT ?o WHERE { ?s ?p ?o }"]],
  ["datasetSerialize", ["h1", "turtle"]],
  ["datasetClose",     ["h1"]] ]
```

`datasetOpen` answers `{"ok":true,"handle":"h1","count":1}`; handles
number "h1", "h2", … per process.

### Common Logic / IKL (Lean flavour only)

CLIF text parses, alpha-normalizes and re-serialises. It does NOT
translate to RDF: the IKL-to-RDF projection and the content-addressed
proposition naming scheme it used were deleted on 2026-08-26
(https://github.com/danbri/factoidal/issues/626), together with the
`clToDataset` and `queryWithIklService` ops and the `x-ikl-*`
entailment-regime family.

Five ops are on the wasm ABI
(https://github.com/danbri/factoidal/issues/623). Every one of them
reports the STRENGTH of its own answer in the envelope, so a caller
never has to go and read the proofs to know what it just got.

```bash
printf '%s' '["(ist c (that (Dead OBL)))"]' > /tmp/cl.json
.lake/build/bin/l4wasm-cli call clParse /tmp/cl.json
# {"ok":true,"sentences":1,"pureCL":false,"normalized":"(ist c (that (Dead OBL)))"}
```

`pureCL` is a DIALECT flag, not a validity signal: true while the text
stays inside ISO/IEC 24707 Common Logic, false from the first IKL
`that` operator onward. The CLI verb is `l4factoidal cl parse FILE`.

`clSerialize(cliftext)` — the canonical writer.

```bash
# {"ok":true,"clif":"(forall (x) (if (Boy x) (Person x)))",
#  "sentences":1,"roundTripProved":false}
```

`roundTripProved` is `false` and stays false until `clif_roundTrip`
(`CL/ClifAdequacy.lean`) is proved: the fragment boundary
`marksLexable` is measured, not proved.

`clAlphaNorm(cliftext)` — the canonical representative of each
sentence's alpha-equivalence class. Bound names become `v1`, `v2`, … in
traversal order, so two sentences differing only in bound names give
byte-identical output. Use it to compare CLIF texts for
alpha-equivalence without a decision procedure.

`clNormalize(cliftext)` — Hayes's reduction of IKL to Common Logic, so
IKL can be handed to a conventional first-order engine.

```bash
# input:  (P (that (Q a)))
# {"ok":true,"head":["(P prop1)"],"tail":["(iff (prop1) (Q a))"],
#  "thatCount":1,"noIntrusion":true,"preserves":"satisfiability", …}
```

⚠️ Two limits, both in the envelope. It preserves SATISFIABILITY, not
equivalence — fit for entailment and consistency testing, not a
transformation to apply to data you intend to keep. And `noIntrusion`
is the PROOF HYPOTHESIS of `tails_satisfiable` / `normalize_preserves`
DECIDED, not a paraphrase: when it is `false` the op still returns the
transformation's output, but no theorem covers that output.

`clFiniteSat(interpJson, cliftext)` — decide satisfaction against a
caller-supplied finite interpretation. Argument 1 names the domain by
LABELS; the op fixes the domain type itself.

```json
{ "domain":    ["bill", "boy"],
  "default":   "bill",
  "names":     { "Bill": "bill", "Boy": "boy", "Sue": "boy" },
  "strings":   { "a string": "bill" },
  "functions": [ { "op": "boy", "args": ["bill"], "value": "bill" } ],
  "relations": [ { "op": "boy", "args": ["bill"] } ],
  "props":     { "(P x)": "bill" } }
```

Only `domain` is required; the rest default to empty and `default` to
the first label. `props` keys are canonical CLIF texts of `that`-bodies.

The answer is worth what `satisfiesFin_eq`
(`CL/FiniteSatTheorems.lean`) says, and its three hypotheses are
discharged or checked rather than assumed. Domain completeness holds by
CONSTRUCTION — the ABI gives the caller no way to name the domain type,
which is `Fin m` over the m labels, with the domain `List.finRange m` —
so a domain omitting an element of its own type is not expressible.
`noSeqQuant` is checked with the same function the hypothesis names,
and a text quantifying a sequence marker is REFUSED:

```json
{"ok":false,
 "error":"refused: the text quantifies a sequence marker, …",
 "precondition":"noSeqQuant"}
```

Read the `preconditions` block of a successful answer rather than
assuming it; a future op may report a condition as checked-and-failed
where this one refuses.

`cl:text` phrases are rejected with a named error (reader gap,
https://github.com/danbri/factoidal/issues/580).

The RDF-side
model theory that reads RDF INTO IKL (`Unified/RdfEmbed.lean`,
`Unified/DatasetEmbed.lean`) is unaffected by the deletion above and is
proved, not projected.
