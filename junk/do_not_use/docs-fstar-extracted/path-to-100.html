Part 1: RDF Parser Failures (25 tests)

All 25 parser failures are in negative syntax tests — the parsers accept invalid input that should be rejected. Positive parsing and eval tests are already at 100%. Each fix adds a validation check; no architectural changes needed.

Fix 1: Reject surrogate code points (U+D800–U+DFFF)

Easy — 10 Turtle failures

Test FileInvalid Input
turtle-syntax-bad-numeric-escape-01..08.ttl\uD800 or \uDFFF in string literals (all 4 quote styles)
turtle-syntax-bad-numeric-escape-09.ttl\uD800 in IRI
turtle-syntax-bad-numeric-escape-10.ttl\uDFFF in IRI
Fix: In parseHexEsc(n) (Turtle line 284, N-Triples line 193), add a range check after parseInt(hex, 16): 
const cp = parseInt(hex, 16);
if (cp >= 0xD800 && cp <= 0xDFFF)
  throw this.err('Surrogate code points U+D800..U+DFFF not allowed');
Node.js String.fromCodePoint(0xD800) silently succeeds, so the check must be explicit. Apply the same fix to both the Turtle and N-Triples parseHexEsc functions.

Fix 2: Reject relative IRIs in N-Triples

Easy — 4 N-Triples failures

Test FileInvalid InputPosition
nt-syntax-bad-uri-06.nt<s>subject
nt-syntax-bad-uri-07.nt<p>predicate
nt-syntax-bad-uri-08.nt<o>object
nt-syntax-bad-uri-09.nt"foo"^^<dt>datatype
Fix: N-Triples forbids relative IRIs (unlike Turtle which can resolve them against a base). After parseIriRef() returns, validate the IRI contains a scheme (: character): 
const iri = parseIriRef();
if (!iri.includes(':'))
  throw new Error('Relative IRIs not allowed in N-Triples');
This check goes in the N-Triples parser only — Turtle correctly allows relative IRIs.

if (c === ' ' || c.charCodeAt(0) < 0x20)

Fix 4: Validate language tag first character

Easy — 1 N-Triples + 1 Turtle failure

Test FileInvalid Input
nt-syntax-bad-lang-01.nt"string"@1
turtle-syntax-bad-lang-01.ttl"string"@1
Fix: Per BCP 47 / LANGTAG production, the first subtag must be [a-zA-Z]+. Digits are only valid in subsequent subtags after a hyphen. Add a check immediately after @: 
const first = peek();
if (!/[a-zA-Z]/.test(first))
  throw new Error('Language tag must start with a letter');
Apply to both N-Triples (parseLiteral line 177) and Turtle (parseLiteralValue line 509).

// Before (wrong):

Part 2: SPARQL Algebra Failures (9 tests)

All 9 failures trace to exactly two root causes in the F*-extracted evaluator. Both can be fixed either in the F* source (preferred) or by patching the extracted OCaml.

Root Cause A: Numeric literal type mismatch (5 failures)

Medium — affects expr-equals, expr-ops, numeric-functions

Problem: When ?v is bound to "10"^^xsd:integer, variable lookup (E_Var) returns ER_Term(T_Literal{...}). But a query literal like 7 evaluates via E_NumericLit to ER_Num(7). When value_compare sees (ER_Term, ER_Num), no match arm handles it — it falls through to the catch-all returning None, which becomes ER_Error, and FILTER drops every row.
TestQuery FilterExpectedGot
expr-equals / eq-int-1FILTER(?o = 1)1 result0
expr-equals / ne-int-1FILTER(?o != 1)2 results0
expr-ops / gt-7FILTER(?v > 7)2 results0
expr-ops / le-10FILTER(?v <= 10)2 results0
numeric-functions / numeric-gtFILTER(?v > 3)1 result0
Fix: Promote numeric-typed literals to native eval_result types at variable lookup. In SPARQL11.Algebra.fst, change the E_Var case of eval_expr: 
| E_Var v ->
    match sm_lookup v mu with
    | Some (T_Literal l) ->
        if lit_datatype l = xsd_integer then
          ER_Num (parse_int (lit_lexical l))
        else if lit_datatype l = xsd_decimal then
          ER_Dec (lit_lexical l)
        else if lit_datatype l = xsd_double then
          ER_Dbl (lit_lexical l)
        else ER_Term (T_Literal l)
    | Some t -> ER_Term t
    | None -> ER_Error
Interim OCaml patch: The same logic can be added to ocaml-patches.sh to patch SPARQL11_Algebra.ml after extraction.

Root Cause B: EXISTS / NOT EXISTS stubbed out (4 failures)

Hard — affects exists suite

Problem: E_Exists and E_NotExists unconditionally return ER_Error in the extracted OCaml (line 2252–2253). EXISTS needs to evaluate a graph pattern against the current graph, but eval_expr only receives (expr, solution_mapping) — it has no access to the graph. This is a forward-reference / dependency cycle issue: eval_expr → eval_pattern → eval_expr_ebv → eval_expr.
TestQuery FilterExpectedGot
exists / existsFILTER(EXISTS { ?s ex:q ?d })1 result0
exists / exists-val(value check on above)1 result0
exists / not-existsFILTER(NOT EXISTS { ?s ex:q ?d })1 result0
exists / not-exists-val(value check on above)1 result0
Fix: Thread the graph into expression evaluation using the existing mutable-ref pattern. The infrastructure is already in place — substitute_pattern (line 3109) exists, and eval_expr_ebv_ref / eval_expr_fwd_ref already solve the eval_expr↔eval_pattern cycle.

Option A (ref cell — OCaml-only, minimal change): 
let current_graph_ref = ref ([] : rdf_graph)

(* In eval_pattern, before calling filter: *)
current_graph_ref := g;

(* In eval_expr: *)
| E_Exists sub_pattern ->
    let g = !current_graph_ref in
    let substituted = substitute_pattern mu sub_pattern in
    let results = eval_pattern substituted g in
    ER_Bool (List.length results > 0)
| E_NotExists sub_pattern ->
    let g = !current_graph_ref in
    let substituted = substitute_pattern mu sub_pattern in
    let results = eval_pattern substituted g in
    ER_Bool (List.length results = 0)
Option B (signature change — F* source, correct fix): Change eval_expr to take (expr, solution_mapping, rdf_graph). This requires updating all callers in the F* source but produces a cleaner extraction.
