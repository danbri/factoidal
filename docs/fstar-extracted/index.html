Browser build: F* extracted to JS and Wasm

The F* specifications in formal/fstar/*.fst are extracted to OCaml, then compiled to JavaScript (via js_of_ocaml) and to WebAssembly (via wasm_of_ocaml). Both artifacts ship from this directory.

JavaScript: w3c-runner.js — self-contained, ~400 KB. Runs in any modern browser or Node.
WebAssembly: w3c-runner.wasm.js (loader, ~45 KB) + w3c-runner.wasm.assets/ (the .wasm binary, ~400 KB). Needs a Wasm-GC-capable engine — Chrome ≥ 119 or Node ≥ 22. Does not run in Firefox yet (Wasm-GC still flagged).

Running from the command line

The quickest way to exercise the artifacts is with Node from a checkout where the W3C test submodule is initialised: 

git clone --recurse-submodules https://github.com/danbri/factoidal.git
cd factoidal/docs/fstar-extracted
node w3c-runner.wasm.js bind
# or the JS variant:
node w3c-runner.js bind

What runs under Wasm today

17 of the 18 SPARQL query/syntax suites and all RDF parser suites reproduce the native-binary results when run via node w3c-runner.wasm.js. The one suite that currently crashes under Wasm is functions, because the SHA/MD5 hash builtins go through C primitives (stub_sha*, caml_digestif_*) that don't yet have Wasm-side bindings. Zarith's ml_z_* primitives do work, via the runtime.wat / runtime_wasm.js pair shipped by zarith_stubs_js v0.17+ (vendored under formal/fstar/ocaml-output/wasm_runtime/).

Build pipeline

F* .fst  ──fstar.exe --codegen OCaml──►  ocaml-output/*.ml
                                         │
                                         ├──ocamlfind ocamlc──►  bin/<platform>/w3c_runner   (native)
                                         │
                                         ├──js_of_ocaml──────►   docs/fstar-extracted/w3c-runner.js
                                         │
                                         └──wasm_of_ocaml────►   docs/fstar-extracted/w3c-runner.wasm.{js,assets/}

See formal/fstar/build-ocaml.sh for the exact invocation.

Browser demo

A minimal interactive demo (load a .ttl file, run a SPARQL query, show results) is a natural next step but isn't wired up yet. The artifact is ready for any page that wants to embed it — import the loader, pass it command-line-style arguments, and read stdout/stderr.
