Browser build: F* extracted to JS and Wasm

The F* specifications in formal/fstar/*.fst are extracted to OCaml and then compiled to JavaScript (via js_of_ocaml) and WebAssembly (via wasm_of_ocaml). Both outputs live in this directory and are rebuilt by CI on every push.

JavaScript: w3c-runner.js — self-contained, ~400 KB. Works in any browser or Node.
WebAssembly: w3c-runner.wasm.js (45 KB loader) + w3c-runner.wasm.assets/ (400 KB wasm binary). Needs a Wasm-GC engine — Chrome ≥ 119, Node ≥ 22. Firefox doesn't enable Wasm-GC by default yet.

Running today

Both artifacts are built as CLI programs: they expect to be invoked with a process.argv (e.g. w3c_runner bind) and they read W3C test files from the local filesystem. They run fine under Node; an in-browser interactive demo is not wired up yet (see “What’s missing” below).

The quickest smoke test, once you have Node 22+ and a checkout of the repo with submodules:

git clone --recurse-submodules https://github.com/danbri/factoidal.git
cd factoidal/docs/fstar-extracted
node w3c-runner.wasm.js bind
# expected: bind pass:10 fail:0 skip:0 unsupported:0

w3c-runner.wasm.js and w3c-runner.js accept the same CLI as the native binary — --list, --all, --rdf, or one or more suite names.

What’s in the vendored wasm runtime

wasm_of_ocaml emits throwing stubs for any external C primitive it can’t link. fstar.lib transitively pulls in zarith (for Prims.int), stdint, sha, and digestif — roughly 150 such primitives in total. js_of_ocaml’s JS stubs don’t link automatically under wasm_of_ocaml; instead you need a companion .wat file that imports the JS functions and re-exports them under the OCaml-facing names. zarith_stubs_js v0.17+ ships exactly that, so we vendor its runtime.wat+runtime_wasm.js under formal/fstar/ocaml-output/wasm_runtime/. (Our opam switch still has v0.16.1 which predates those files.)

The remaining stdint / sha / digestif primitives get identity pass-through shims applied by wasm_stub_shims.py — that’s enough for stdint (it’s linked for module init but not used on the hot path) and also for the non-hash SPARQL suites (which never call caml_digestif_*). The moment a query invokes MD5/SHA, though, the identity shim returns the wrong shape and V8 raises RuntimeError: illegal cast. Fix is the same recipe: vendor or write .wat + runtime_wasm.js for sha and digestif.c.

What’s missing for an interactive browser demo

There is no “paste a query, click Run” demo here yet. The wasm binary is a CLI — to use it from a browser page we need one of:
  • A second entry point compiled alongside w3c_runner that exposes SPARQL evaluation as a JS-callable function (factoidal_eval(data: string, query: string): string), so we don’t need to fake argv and filesystem reads.
  • Or a browser-side shim that populates wasm_of_ocaml’s in-memory MlFakeDevice with the W3C test manifests and drives w3c_runner with a synthetic process.argv.
Either is straightforward follow-up work; neither is done today.

Build pipeline

F* .fst  ──fstar.exe --codegen OCaml──►  ocaml-output/*.ml
                                         │
                                         ├──ocamlfind ocamlc──►  bin/<platform>/w3c_runner   (native)
                                         │
                                         ├──js_of_ocaml──────►   docs/fstar-extracted/w3c-runner.js
                                         │
                                         └──wasm_of_ocaml────►   docs/fstar-extracted/w3c-runner.wasm.{js,assets/}

See formal/fstar/build-ocaml.sh for the exact invocation. ./build-ocaml.sh runs the native + JS pipeline; ./build-ocaml.sh wasm adds the WebAssembly step (it needs wasm_of_ocaml-compiler and a current-enough binaryen — see js_of_ocaml#2190 if your distro’s binaryen package is missing wasm-merge).
