How a module earns each bucket

  • Shipping function — a name that appears as a top-level value binding in ocaml-output/<Module>.ml. Extraction, not naming, is the oracle. Extracted types do not count.
  • Declarative relation — a top-level definition F* erases (absent from the extracted .ml) whose return type is prop, Type0 or logical. That is formalised specification.
  • Pure formalisation module — in the build module list, yet extracts to no .ml at all: verified on every extract run, contributing zero executable code.
  • W3C-refinement theorem — names a shipping function and a declarative relation from a different pure formalisation module, so the specification is stated independently of both the code and the proof.
  • Internal-refinement theorem — names a shipping function and a declarative relation, but the relation lives beside the code it constrains: an invariant, not an independent formalisation.
  • Algorithm-correctness theorem — relates two or more shipping functions, with no declarative relation.
  • merely Tot — the module has shipping functions and no lemma anywhere in the corpus mentions them.

Name resolution is limited to the host module plus the modules it opens or aliases; an ambiguous identifier is dropped rather than counted. The classifier therefore fails downward — a module can be under-credited here, never over-credited.
