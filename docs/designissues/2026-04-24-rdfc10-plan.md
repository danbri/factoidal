# RDF Dataset Canonicalization 1.0 (RDFC-1.0) — Plan

Date: 2026-04-24
Status: plan + scoping; no implementation yet

## What RDFC-1.0 is

W3C recommendation: <https://www.w3.org/TR/rdf-canon/>. An algorithm
that takes an RDF dataset (possibly with blank nodes and multiple
named graphs) and produces a canonical N-Quads serialisation — same
triples in same byte-order regardless of input formatting, parse
order, or blank-node label choice. Core mechanism: a Hogan-style
deterministic blank-node re-labelling via iterated hashing of
graph-neighbourhoods, plus a canonical quad-order sort.

Inputs that represent the same abstract dataset (isomorphic modulo
blank-node renaming) produce byte-identical output. This enables:

- Cryptographic graph identity via `sha256(canonical_nquads)`.
- Verifiable Credentials data-integrity proofs (the `vc` submodule
  depends on this).
- Deduplicating graph stores that hash graphs as keys.
- Reproducible diffs across bnode-relabelling noise.

## Why it matters for Factoidal

Three existing design docs all point at RDFC-1.0 / URDNA2015 (its
pre-REC predecessor) as the target algorithm for graph identity:

- `docs/designissues/attestation-model.md` — signed-graph flow needs
  a canonical form to bind signatures to.
- `docs/designissues/kgx-pipeline.md` — Step 3 of the KGX pipeline:
  "Canonicalize the merged graph (URDNA2015 / RDFC-1.0)".
- `docs/designissues/graphflow.md` — identical framing.

Plus it's the enabling primitive for the `vc` submodule we just
vendored at `third_party/testing/vc/`. Without RDFC-1.0 we can't
plausibly run VC data-integrity tests.

## Existing primitives we can reuse

- `formal/fstar/ocaml-output/fstar_pure_hashes.ml` — pure OCaml
  (ultimately pure F\*) MD5 / SHA-1 / SHA-256 / SHA-384 / SHA-512.
  Already stack-safe and already on the C-extraction roadmap. RDFC-1.0
  is specified in terms of SHA-256 (`rdfc:SHA256`) with an optional
  SHA-384 variant — both available.
- `rdf_graph` / `rdf_term` / `bnode_id` types in
  `RDF.Graph.Executable` — already model triples and quads; datasets
  via `rdf_dataset` (default graph + list of named graphs).
- Our Turtle/TriG/N-Quads parsers can produce the dataset input.
- Canonical N-Quads serialiser — we have N-Triples output in
  `factoidal_cli`; extending to quads is minor.

## Test corpus

Vendored submodule at `third_party/testing/rdf-canon/`. Tests live at
`third_party/testing/rdf-canon/tests/rdfc10/`, indexed by
`tests/manifest.ttl`. Three test types per the manifest header:

- `rdfc:RDFC10EvalTest` — positive evaluation: given input
  `testNNN-in.nq`, expect output `testNNN-rdfc10.nq`.
- `rdfc:RDFC10NegativeEvalTest` — input that RDFC-1.0 is expected to
  reject (currently none in the suite's `mf:entries` list, per quick
  grep, but the type is reserved for future additions).
- `rdfc:RDFC10MapTest` — input plus expected *issued-identifier map*
  (`testNNN-rdfc10map.json`): tests not just the canonical nquads but
  the full `_:e0 → _:c14n0` relabelling map.

**Counts (2026-04-24 from upstream):** 89 `mf:entries`, ~45 distinct
input files and ~60 expected outputs after dedup (each `cNNN` has a
companion `mNNN` map test sharing the same input).

**Shape of a minimal test.** `test001-in.nq`:

```
_:e0 <http://www.w3.org/1999/02/22-rdf-syntax-ns#type> <http://example.org/vocab#Foo> .
```

`test001-rdfc10.nq` (expected canonical form):

```
_:c14n0 <http://www.w3.org/1999/02/22-rdf-syntax-ns#type> <http://example.org/vocab#Foo> .
```

Trivial case: rename the single bnode `_:e0` → `_:c14n0`. Harder
cases cover cycles, symmetric sub-graphs, named graphs, literals with
datatypes, etc.

## Proposed F\* module layout

```
formal/fstar/
  RDF.Canon.fst            // core algorithm: first-degree hash,
                           // issue-identifier loop, n-degree hash
  RDF.Canon.Serializer.fst // canonical N-Quads emitter (sort quads,
                           // emit each as canonical N-Quad line)
```

Wired into:

- `formal/fstar/ocaml-output/factoidal_cli.ml` — new flags
  `--canonicalize` (emit canonical N-Quads) and `--canonical-hash`
  (emit `sha256(canonical_nquads)`).
- `formal/fstar/ocaml-output/rdfc10_runner.ml` (new, hand-authored) —
  parallel to `owl_runner.ml`, reads the rdf-canon manifest and
  reports per-test pass/fail.
- `formal/fstar/build-ocaml.sh` — extract new F\* modules, compile
  `rdfc10_runner` binary.

Algorithm shape (paraphrased from spec §3.1 and §3.2):

```fstar
// Each blank node's first-degree hash: hash of the quads it is
// incident to, with its own label replaced by "a" and other bnodes
// replaced by "z", sorted and concatenated.
val first_degree_hash : rdf_dataset -> bnode_id -> string

// Issue a canonical identifier from the issuer state (a map +
// list; we use a functional state record here to stay ref-free).
noeq type issuer = { issued : list (bnode_id * string); counter : nat }
val issue_identifier : issuer -> bnode_id -> (string * issuer)

// n-degree hash: for a blank node b, walk its neighbourhood,
// recursively hashing each adjacent bnode's own n-degree hash
// (with the issuer state passed along), returning an (hash, issuer)
// pair. Fuel-indexed to guarantee termination.
val hash_n_degree_quads
  : rdf_dataset -> bnode_id -> issuer -> fuel:nat
  -> Tot (string * issuer) (decreases fuel)

// Top-level: take the dataset, compute first-degree hashes for all
// bnodes, process bnodes in hash-sorted order, issuing identifiers
// and running n-degree for unresolved cases, return the final
// relabelled dataset.
val canonicalize : rdf_dataset -> rdf_dataset
val canonical_nquads : rdf_dataset -> string
```

All `noeq` uses are structural records; should survive KaRaMeL with
straightforward struct-by-value C emission.

## Phased plan

### Phase 0 — test harness skeleton (NEXT COMMIT)

Hand-authored `formal/fstar/ocaml-output/rdfc10_runner.ml` that:

1. Parses `third_party/testing/rdf-canon/tests/manifest.ttl` via
   `Parser_Turtle.parse_turtle_with_base`.
2. Extracts entries with `rdf:type rdfc:RDFC10EvalTest` (and the other
   two rdfc: types).
3. Per test: prints `identifier | type | input-file | result-file |
   STUB`.
4. Emits a final labelled count per rule #25:
   `RDFC-1.0 tests: 0 pass, 0 fail, 89 stub (out of 89)`.

`build-ocaml.sh` gets a 3rd runner binary added alongside `w3c_runner`
and `owl_runner`.

### Phase 1 — first-degree hash + trivial cases

Implement `first_degree_hash` and a simple canonicalise that relabels
only bnodes with unique first-degree hashes (no iteration). This
clears roughly the 30-40 "low computational-complexity" tests in the
suite (test001–test020 are mostly these). Target: **50 % of RDFC-1.0
suite passing after Phase 1.**

### Phase 2 — full issuer / n-degree hash

Add the `hash_n_degree_quads` recursion. This is the hard part:
- Fuel bound: # of blank nodes squared is the theoretical worst case;
  we can start with `max(32, n_bnodes × 4)` and revisit empirically.
- Permutation enumeration for cycle cases: RDFC-1.0 §4.9 describes an
  explicit permutation loop; in F\* we'll use `List.Tot.sort` + fold
  rather than mutating permutations in place.

Target: **~95 % of the suite** after Phase 2. Residual failures are
likely edge cases in unicode handling or N-Quads quoting.

### Phase 3 — CLI exposure

`factoidal --canonicalize input.nq` emits canonical N-Quads to stdout.
`factoidal --canonical-hash input.nq` emits
`sha256(canonical_nquads)` in lowercase hex.

Route these through `OWL_QueryEval`-style wrappers? No — canonicalisation is independent of SPARQL evaluation, so it's a
direct call on `RDF.Canon.canonicalize`.

### Phase 4 — Integration into attestation-model

Once the numbers are solid: wire `canonical_hash` into the
graph-assertion / signing flow outlined in `attestation-model.md`.

### Phase 5 — C-extraction readiness

The algorithm uses only:

- String hashing (pure F\* via `fstar_pure_hashes` — clean).
- Byte-indexed string ops (`Parser.FastString` — clean).
- List / fold / sort over algebraic-data-type records (KaRaMeL-clean).

No `Dv` effect, no OCaml-runtime deps. Should extract to C without
drama. Open question: `FStar.List.Tot.sortWith` extraction — if
KaRaMeL emits it as a recursive merge sort that's fine; if it bottoms
out on a `qsort_*` primitive we may need a C stub.

## Open questions

1. **Hash primitive default**: spec says SHA-256 is the default for
   RDFC-1.0; SHA-384 variant exists. Pick SHA-256 for the CLI flag,
   expose `--canonical-hash-algo sha384` as an opt-in.
2. **Bnode label collisions**: if an input already has a bnode
   labelled `_:c14n5`, the spec reserves the `c14n` prefix for the
   algorithm's own output. Our canonicaliser must preserve the input
   label but emit the algorithm-assigned label in output; if the
   algorithm's label coincides with an input label, we end up with a
   collision. Spec §3.2 handles this by the issuer always generating
   fresh identifiers, regardless of what's in the input — we follow
   suit.
3. **Fuel bound default**: start at `max(32, n_bnodes × 4)`; revisit
   after Phase 1 testing reveals whether the harder tests need more.
4. **Sort primitive**: spec uses lexicographic byte-wise sort for
   quad-ordering. Use `List.Tot.sortWith` with our N-Quad canonical
   string compare.

## Known gotchas (from spec skim)

- **Dataset vs graph**: RDFC-1.0 canonicalises *datasets* (named
  graphs included). The graph-name slot is part of the quad-sort key.
  Don't collapse to default graph.
- **Isomorphism classes**: the algorithm outputs a deterministic
  representative per class; multiple non-identical inputs that are
  isomorphic produce the same output. Correct behaviour by design.
- **Complex cases**: cycles of bnodes with no distinguishing structure
  (common case: 2-bnode symmetric rings) require the n-degree loop;
  these are the tests that will fail in Phase 1 and pass only in
  Phase 2. Test names like `test043c`, `test063c` mention
  "computationalComplexity: high" — those are the stress cases.
- **Unicode**: N-Quads allows \\uXXXX escapes; the canonical form
  re-emits them in a specific way. We already have UTF-8 handling via
  `Parser.FastString`; should be fine.

## Acceptance criteria

1. `rdfc10_runner` compiles + runs + emits labelled score.
2. Phase 1 target: "RDFC-1.0 tests: 35+ pass, 0 fail, rest stub (out of 89)".
3. Phase 2 target: "RDFC-1.0 tests: 80+ pass (out of 89)".
4. `factoidal --canonicalize` produces byte-identical output for
   isomorphic inputs (hand-verify against `test003-in.nq` vs a
   relabelled copy).
5. SPARQL sweep unchanged (no regressions in
   `third_party/testing/w3c/sparql/sparql11`).

## Non-goals (for now)

- URDNA2015 (the pre-REC predecessor) — supersede by RDFC-1.0; we
  don't attempt both.
- C14N mode selection / Map mode — our runner covers both via the
  RDFC10EvalTest + RDFC10MapTest shapes, but we'll defer Map-test
  support to Phase 2.
- Performance tuning / parallelisation — get it correct first, then
  look at hot-path profiling if needed.
