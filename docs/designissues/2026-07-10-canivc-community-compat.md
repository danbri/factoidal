## What canivc.com is

Digital Bazaar's static 11ty site, "Can I Credential?" — a "community
compatibility dashboard for Verifiable Credentials" aggregating W3C VC
Working Group and CCG test-suite interoperability reports across
~20 implementations. It does not run tests itself: it fetches each
suite's own published `index.json` report (generated by
`@digitalbazaar/mocha-w3c-interop-reporter`) from
`w3c.github.io/<suite>/index.json` or `w3c-ccg.github.io/<suite>/index.json`
(URL list in `digitalbazaar/canivc`'s `src/_data/results.js`) and
renders matrices from it. Ten reports as of the crawl date:

## Execution model (why "run the suite" means what it means here)

Every suite is a **mocha** test project. Test files call
`filterByTag()` from `vc-test-suite-implementations` (VC WG suites) or
`w3c-ccg/vc-test-suite-implementations` (CCG suites) to find registered
implementations by tag, then drive each one's HTTP endpoints —
`POST /credentials/issue`, `POST /credentials/verify`, sometimes
`POST /credentials/derive` or `GET /didResolvers/<did>` for DID
resolution. **Local testing is supported without registering an
implementation**: drop a `localConfig.cjs` (no leading dot — the
suites' own example files say `.localConfig.cjs`, but
`vc-test-suite-implementations/implementations/index.js` actually
calls `getLocalManifest('localConfig.cjs')`; the leading-dot filename
in the example files silently does nothing, confirmed by tracing the
loader) at the suite's root with `testAllImplementations: false`, and
the suite tests ONLY the implementations you list — otherwise it
merges your entry into the full live community registry and attempts
network calls to ~8 unrelated real endpoints (apicatalog.com, Trinsic,
bovine.social, etc.), most of which fail or time out in a sandboxed
environment. This one filename gotcha is why the first two runs of the
eddsa suite here scored 32 passing / lots of unrelated network
failures before the fix — worth flagging for whoever touches this next.

## What we can run now (measured)

### `eddsa-rdfc-2022` — `.github/test-suites/vc-di-eddsa.yaml`

Vendored `w3c/vc-di-eddsa-test-suite` at commit `769275c968c608799939aa25bb32869ce76a8e10`
into `third_party/testing/vc-di-eddsa/` (PROVENANCE.md there). Built
`bin/vc-api-shim/server.mjs`, a plain-Node HTTP adapter with zero
VC/RDF semantic logic of its own — every `verified`/signing outcome is
exactly what `npm/factoidal`'s public API
(`parse`/`canonicalize`/`vcEddsaCreateFromCanonical`/
`vcEddsaVerifyFromCanonical`/`vcEd25519SecretToPublic`) returned, the
same functions `npm/factoidal/test/vc-crypto*.test.js` exercises.
Ran the create + verify test files (`05-di-rdfc-create.js`,
`15-di-rdfc-verify.js` — the same 16 + 15 = 31 tests as canivc's
"eddsa-rdfc-2022 issuers" + "eddsa-rdfc-2022 verifiers" matrices,
directly comparable):

**26 pass, 5 fail (out of 31) — 83.9%.**

Community comparison on the identical 31-test scope (issuers +
verifiers combined, computed from the snapshot): scores range
0% (Trinsic, bovine) to 100% (Grotto Networking), median 41.9%
(apicatalog.com and Procivis One Core tie at 41.9%). **83.9% places
Factoidal above the community median, below Grotto Networking (100%)
and SpruceID (96.8%), roughly level with Trential (93.5%).**

Remaining 5 failures, all a single root cause each:
- 3 failures: no `DATA_LOSS_DETECTION_ERROR` — the shim doesn't detect
  a JSON-LD term silently dropped by expansion (undefined type on
  issuance, undefined term added post-issuance on verification, no
  `credentialSubject`) and reject; it just signs/verifies whatever it's
  given.
- 2 failures: multi-proof documents (`proof` as an array,
  `proof.previousProof` chaining) aren't supported — the shim checks
  exactly one proof.

`30-rdfc-interop.js`, `70-data-model.js`, `80-algorithms.js` are **not
run**: all three import the suite's own `tests/vc-generator/contexts.js`,
which crashes at module load (`DOMException [DataCloneError]: Cannot
clone object of unsupported type` from `structuredClone()`) under this
Node version — an upstream/environment bug in the vendored suite's own
dependency chain, not something a shim fix can address.
`60-jcs-interop.js` is skipped by design: see the eddsa-jcs-2022
decision below.

### VC Data Model 2.0, HTTP issuer/verifier suite — `.github/test-suites/vc20-api.yaml`

The suite at `third_party/testing/vc` was already vendored (used by
the existing `vc_stage1` structural-fixture suite, `.github/test-suites/vc.yaml`,
117 pass / 0 fail via `bin/vc-runner` — no HTTP involved there). This
task additionally ran the SAME vendored suite's own mocha
issuer/verifier test files (`1.03-conformance.js` through
`7-algorithms.js`, 14 files) as real HTTP round trips against the
shim:

**22 pass, 37 fail (out of 59) — 37.3%.**

Single dominant cause for essentially all 37 failures (see
`gap_summary` in `docs/test-results/by-suite/vc20-api.json`): the shim
has no VC Data Model 2.0 structural validator. It signs/verifies
whatever JSON-LD it's handed; it does not reject malformed
`credentialStatus`/`refreshService`/`credentialSchema`/`termsOfUse`/
`evidence` shapes, a `validUntil` before `validFrom`, a missing
`type`/`@context`, or a malformed Verifiable Presentation. Closing this
gap needs `VC.Credential.fst`'s structural checker (already used by
`vc_stage1`) wired to a new npm ABI export — deliberately not attempted
here, since hand-writing equivalent checks in the shim would be exactly
the "no semantic logic in test runners" anti-pattern (#15). This is a
DIFFERENT, complementary measurement from `vc_stage1` — do not add the
two scores together; one is a structural-fixture check with no HTTP or
signing, the other is an HTTP+signing round trip with no structural
check.

### did:key

Assessed, not implemented in this pass. `w3c-ccg/did-key-test-suite`'s
"did:key Create Operation" matrix (misleadingly named — it's a
**resolver conformance** suite: `GET /didResolvers/<did>` returning a
DID Resolution Result) requires: (1) the
`{didDocument, "@context", didDocumentMetadata, didResolutionMetadata}`
envelope per the DID Resolution spec, (2) specific structured error
codes (`invalidDid`, `methodNotSupported`, `invalidPublicKeyLength`,
etc.) for malformed inputs, (3) a versioned-DID parsing convention
(`splitDid` in the suite's `helpers.js` expects a numeric version
segment) that plain `did:key:z6Mk...` doesn't carry. Factoidal's
`didKeyResolve` npm export (F*-verified, `DID.Key.fst`) returns bare
RDF (an N-Triples DID Document with `publicKeyMultibase`, verification
relationships), not this envelope — real adapter work, not a thin
wrapper. Given the timebox, this is recorded as a scoped-out stretch
goal rather than a half-built route; `.github/test-suites/did.yaml`'s
existing `did_key` vector suite (8 pass, 0 fail of 8, unaffected by
this task) remains the only did:key measurement.

## Out of scope, with reasons

- **BBS (`vc-di-bbs`):** no BBS signature scheme anywhere in the
  codebase (HACL* doesn't ship BBS; it would need a fresh crypto
  vendor decision per `skills/crypto-policy/SKILL.md`, not a wiring
  task).
- **ECDSA (`vc-di-ecdsa`):** HACL* DOES vendor P-256 source
  (`third_party/hacl/PROVENANCE.md` lists it as an "unrelated
  primitive" alongside Blake2/HPKE/MD5/SHA-1) but it is not wired to
  any `assume val` realisation, and `VC.DataIntegrity.fst` has no
  `ecdsa-rdfc-2019`/`ecdsa-jcs-2019` cryptosuite algorithm. This is
  real, scoped future work (HACL* P-256 adoption + a new cryptosuite
  module mirroring `eddsa_rdfc_2022_*`), not attempted here.
- **JOSE/COSE (`vc-jose-cose`):** JWT/CWT securing is a different
  serialization stack (compact JWS, not RDF Dataset Canonicalization);
  no JWT signing exists in the codebase.
- **Bitstring Status List (`vc-bitstring-status-list`):**
  `credentialStatus` processing (fetch the status list credential,
  decode the bitstring, check the bit) is not implemented anywhere;
  `VC.Credential.fst`'s header explicitly defers `credentialStatus`
  inner-shape checks to a later stage.
- **VC-API full issuer/verifier suites (`vc-api-issuer`,
  `vc-api-verifier`):** these test the FULL VC-API surface (exchanges,
  credential status updates, DID resolution endpoints, presentation
  exchange, OAuth2/zcap authorization) — an order of magnitude more
  surface than `/credentials/issue` + `/credentials/verify`. The shim
  built here covers exactly those two operations and does not attempt
  the rest.
- **`ed25519signature2020` (legacy cryptosuite):** distance from
  `eddsa-rdfc-2022` is real, not cosmetic — different proof
  serialization (`jws` field instead of `proofValue` multibase, LD-Signatures
  canonicalization framing predates Data Integrity's transform/hash/proof
  split) and a different, older `@context`
  (`https://w3id.org/security/suites/ed25519-2020/v1`). Assessed and
  parked rather than attempted; the existing eddsa-rdfc-2022 machinery
  does not generalize to it without real cryptosuite-specific work.
- **`eddsa-jcs-2022`:** decided NOT trivial after evidence, not
  assumed. JCS (RFC 8785 JSON Canonicalization Scheme) canonicalizes
  the JSON *document* directly — no RDF, no `@context` resolution, no
  RDFC-1.0 — a completely different transform step from the one
  `VC.DataIntegrity.fst`'s `transform_dataset` implements
  (`RDF.Canonical.canonicalize_to_nquads`). Supporting it would mean a
  second, JSON-canonicalization transform path end to end, not a flag
  on the existing one. Recorded as a real, scoped gap in
  `.github/test-suites/vc-di-eddsa.yaml`'s `remaining` list, not
  attempted.

## Technical notes for whoever picks this back up

- **`localConfig.cjs` filename:** no leading dot, despite what every
  vendored suite's own `localConfig.example.cjs` header comment says.
  Traced to `vc-test-suite-implementations/implementations/index.js`'s
  `getLocalManifest('localConfig.cjs')` call. Get this wrong and the
  suite silently merges in the full live community registry instead of
  testing just your implementation — the failures look like your
  server is broken; they're actually `bovine.social` being unreachable.
- **`credentials-v2.jsonld` + `security-data-integrity-v2.jsonld`
  together = parse failure.** `credentials-v2.jsonld` already carries a
  scoped `DataIntegrityProof` term definition (with `cryptosuite`,
  `verificationMethod`, `proofPurpose`, `created`, `proofValue` all
  resolvable from inside it — confirmed by direct testing). Appending
  `security-data-integrity-v2.jsonld` on top redefines those same
  `@protected` terms and the engine rejects the combined document.
  `bin/vc-api-shim/server.mjs`'s `proofContextFor()` only appends the
  DI context when v2 (or the DI context itself) isn't already present
  — needed for VC 1.1-context credentials (whose base context has no
  Data Integrity vocabulary at all), harmful for VC 2.0-context ones.
- **Response-shape disagreement between the two vendored suites'
  clients.** `vc-di-eddsa-test-suite` calls through
  `vc-test-suite-implementations`' `makeHttpsRequest`, which
  unconditionally unwraps `data.verifiableCredential` if present.
  `vc-data-model-2.0-test-suite`'s own local `TestEndpoints.js`
  branches on URL scheme: for `https://` it also goes through that
  same unwrapping client, but for `http://` (the suites' own documented
  local-testing mode) it uses a raw `http.request` with NO unwrapping,
  so it needs the credential's fields at the top level of the response
  body. The shim's `/credentials/issue` response satisfies both by
  spreading the credential's fields at the top level AND including the
  `verifiableCredential` wrapper key — same data, two access paths, not
  two different answers.
- **No JSON-LD remote-context loader in the npm ABI.**
  `JSONLD.Loader.fst` is a documented assume-val I/O seam
  (`bin/npm-entry/entry_jsoo.ml` registers no documentLoader for this
  consumer). The shim carries a small local context registry
  (`third_party/contexts/`: `credentials-v1.jsonld`,
  `credentials-v2.jsonld`, `credentials-examples-v2.jsonld`,
  `security-data-integrity-v2.jsonld`, `security-multikey-v1.jsonld`)
  and inlines matching `@context` IRIs before calling `parse()`. A
  document referencing any other context fails to parse — an honest,
  visible failure, not a silent skip.
- **did:key construction has no ABI export.** `didKeyResolve` (the
  reverse direction — did:key string to DID Document) is F*-verified
  and exposed; building a did:key identifier FROM a raw public key is
  not. The shim implements base58btc encode/decode +
  Ed25519-multicodec (`0xed 0x01`) tagging by hand
  (`bin/vc-api-shim/server.mjs`, mirroring `VC.Multibase.fst`'s
  `ed25519_multicodec_prefix`/`multibase_encode_base58btc`) — wire-format
  transcoding, not verification logic; every actual correctness
  decision still routes through the engine.
