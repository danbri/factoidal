## Measurement corrections, 2026-08-23

The coverage figure moved several times in one day, and three of those
moves came from a wrong AUDIT rather than from landed code. Each
correction is recorded here with the method that produced the wrong
answer, because the next reader needs to know which number they are
looking at.

### First: module-name matching, and what it cannot see

`DID.Key` turned up by hand as covered by `L4Factoidal/VC/DidKey.lean`
all along. I audited the rest of the not-covered list by squashed MODULE
NAME, found nothing more, and wrote "an audit of the whole not-covered
list found no other false negative".

That method cannot see two things, and both were present:

1. **A consolidation** — one Lean module covering two F\* modules under a
   third name. `L4Factoidal/RDF/Entailment.lean` covers BOTH
   `RDF.Entailment.Simple` (182) and `RDF.Entailment.Regime` (271); its
   own header says so in its first sentence.
2. **A substantive rename** — `Parser.CSVResults` (610) became
   `SPARQL.ResultsCsvTsv`.

A definition-name audit — every `let` / `val` / `type` of each
not-covered F\* module against every `def` / `abbrev` / `structure` /
`inductive` / `theorem` in the Lean tree, normalised for case and
underscores — found those.

### Second: the method that was in the tree all along

**A Lean module's header names the F\* module it ports.** Extracting
every `formal/fstar/X.fst` mention from every Lean header, and reading
the sentence around each, settles the question directly. That found five
more genuinely covered engine modules, 3,015 F\* lines:

|---|---|---|
| `RDF.Entailment.RDFS.RhoDFClosure` | 1996 | `RDFS/RdfsCore.lean` — "Ports the rule set of" |
| `RDF.IRI` | 530 | `Syntax/IriResolve.lean` — "Port of" |
| `Parser.SRX` | 291 | `SPARQL/ResultsXml.lean` — "Port of … (parsing)" |
| `Parser.JSONResults` | 160 | `SPARQL/ResultsJson.lean` — "Port of … (parsing)" |

⚠️ Two of those claims are PARTIAL: `RdfsCore.lean` ports the RULE SET,
not `RhoDFClosure`'s five theorems, and the two Results modules port the
PARSING halves plus the serialising halves of `SPARQL.Protocol.fst`, not
everything in the F\* files.

Reading the headers also settled two the other way, which a ratio-based
audit would have counted as near-misses:

- `SPARQL.FullText` (223) is NOT covered, and `SPARQL/Parser.lean` says
  so: "whose encoding lives in `SPARQL.FullText.fst` — no Lean".
- `JSONLD.Frame` (335) is NOT covered. `JSONLD/Expand.lean` merely lists
  it beside `Compact.fst` and `Flatten.fst` as a sibling.

`Parser.JSONLD` (1459) is claimed only as "Port of the **toRdf half**"
by `JSONLD/ToRdf.lean`. The expand, compact and flatten halves have
their own Lean modules; whether the union is complete has not been
checked, so it stays in the not-covered column rather than being counted
on a guess.

### One narrow behavioural gap inside the coverage

The F\* `match_term` takes a POSITION-AWARE literal comparison,
`leq : inside_tt -> literal -> literal -> bool`, because a directional
language string is opaque — compared case-sensitively — only INSIDE a
triple term. Lean's `entailsWith` takes `leq : Literal -> Literal ->
Bool` with no position flag. The coverage is substantive but not
complete, and the difference is what the W3C
`opaque-dir-language-string` fixtures exercise.

### The rule

An audit that finds nothing is evidence about the AUDIT's reach before
it is evidence about the code. State the method next to the result, and
pick one that can see the failure you are looking for. Full text: hazard
#28 in `skills/workflow-gotchas-debugging`, anti-pattern #28 in
CLAUDE.md.

### On the proof column

These are F\* modules whose content is a proof about the F\*
implementation: `.Spec`, `.Refinement`, `.ModelTheory`,
`.Completeness`, `.Axioms`, `.RoundTrip`. The Lean tree carries its
own theorem modules (`*Theorems.lean`, `RLTheorems`,
`TableauTheorems`, `SyntaxTheorems`, and the `#guard` layer), so a
module-for-module port is not the right measure of this column. What
IS the right measure — which obligations the F\* discharges that the
Lean does not — has not been computed. Recording that as unknown
rather than as zero.

### On the F\*-only column

`Parser.FastString.*`, seven modules. The F\* parser indexes raw
UTF-8 bytes, so it needs machinery to rebuild codepoints from bytes
and reject invalid sequences. Lean's `String` and `Char` are
codepoint types and `Char` is a valid scalar value by construction,
so that machinery has no counterpart. `L4Factoidal/XML/Document.lean`
states this in its header.


### Third: the tool read a cache instead of the repository

`tools/lean-port-gap.py` took both module lists from two text files in
the session scratchpad. The F\* list was stable, but the Lean list was a
snapshot, and it was written before the last ports. So a freshly landed
module — `RDF.CottasStore.CompoundPresenceWriter` — was reported as NOT
COVERED by the tool that exists to answer exactly that question, while
its Lean file sat in the tree.

The scratchpad is per-session and is deleted with the container, so the
same tool would also have crashed on a fresh session rather than
reporting a stale answer. Both failures have one cause: a measurement
tool whose input a person has to remember to refresh.

The tool now walks `formal/fstar/*.fst` and
`formal/lean4/L4Factoidal/**/*.lean` on every run and exits non-zero if
either walk comes back empty. There is no cache left to go stale.
