# RFC 3986 §5.2 IRI resolution — v2 plan (subagent-ready)

**Date:** 2026-04-21. Read-only planning for a single future commit.
**Scope:** Reference resolution only — RFC 3986 §5.2 *Transform References*
plus the helpers it calls (§5.2.3 merge, §5.2.4 remove_dot_segments, §5.3
recomposition, and enough of §3 to parse a base/ref into components).
IRI parsing beyond what §5.2 needs is **out of scope**.

Supersedes:
`docs/designissues/2026-04-19-rfc3986-iri-resolution-plan.md` (v1).
The v1 plan was implemented and reverted because the subagent could not
close the F* verification obligations inside its stream budget. The
arithmetic on byte positions + `option string` plumbing in a
`noeq`-record world kept tripping Z3. Two things have changed since then:

1. `Parser.FastString` now exists (commit `c32b088`), extended in Pass 2
   (commit `70dafe0`) with `fs_cp_at` / `fs_cp_len`. All scanners have
   migrated to `fs_byte_length` / `fs_byte_at` / `fs_byte_sub` /
   `fs_find_byte`. The refinement pattern
   `pos : nat{pos <= fs_byte_length s}` + explicit `fuel : nat` +
   `decreases fuel` is proven to verify on hot-path scanners.
2. RFC 3986 reference resolution is ASCII-only by construction: every
   delimiter the algorithm branches on (`:`, `/`, `?`, `#`, `.`) is a
   single ASCII byte. We do not need codepoint semantics for any
   decision — non-ASCII bytes inside authority/path/query/fragment are
   carried through as opaque byte runs. That means v2 can stay on the
   byte primitives end-to-end, dodging the `FStar.String.length` cost
   model that hurt v1 and avoiding the codepoint decoder entirely.

The v2 plan below is intentionally a drop-in for Parser.Turtle's current
`resolve_iri_hint` call sites. No semantics are added beyond §5.2; no
percent-encoding normalisation, no case folding, no IDN, no Unicode
normalisation.

## §1. Algorithm (RFC 3986 §5.2, verbatim pseudo-code)

### §1.1 Transform References (§5.2.2)

Given a parsed base `Base` (guaranteed to have a scheme, per §5.2.1
pre-condition) and a parsed reference `R`, produce the target `T`:

```
if defined(R.scheme):
    T.scheme    = R.scheme
    T.authority = R.authority
    T.path      = remove_dot_segments(R.path)
    T.query     = R.query
else:
    if defined(R.authority):
        T.authority = R.authority
        T.path      = remove_dot_segments(R.path)
        T.query     = R.query
    else:
        if R.path = "":
            T.path = Base.path
            if defined(R.query):
                T.query = R.query
            else:
                T.query = Base.query
        else:
            if R.path starts with "/":
                T.path = remove_dot_segments(R.path)
            else:
                T.path = merge(Base, R.path)      // §5.2.3
                T.path = remove_dot_segments(T.path)
            T.query = R.query
        T.authority = Base.authority
    T.scheme = Base.scheme

T.fragment = R.fragment
```

(RFC 3986, §5.2.2, lines "if defined(R.scheme) then" through
"endif; endif; endif". The textual source is reproduced verbatim in the
RFC; above is the canonical pseudo-code presentation.)

### §1.2 Merge (§5.2.3)

```
merge(Base, ref_path):
    if defined(Base.authority) and Base.path = "":
        return "/" ++ ref_path
    else:
        // "all characters of Base.path up to, but not including,
        //  the right-most slash (/)"; if no slash, result is empty.
        return prefix_up_to_last_slash(Base.path) ++ ref_path
```

### §1.3 remove_dot_segments (§5.2.4)

Two-buffer loop. Input is the full path string; output is accumulated.
At each iteration, inspect the **start of input**:

```
repeat until input is empty:
    A.  if input begins with "../" : strip "../"
        else if input begins with "./" : strip "./"
    B.  else if input begins with "/./" : replace with "/"
        else if input = "/." : replace with "/"
    C.  else if input begins with "/../" : replace with "/"
                                            and pop the last segment
                                            from output
        else if input = "/.." : replace with "/" and pop last segment
    D.  else if input = "." or ".." : strip it (input becomes "")
    E.  else: move the first path segment from input to output
              — i.e. the leading "/" if any, then everything up to
              (but not including) the next "/". Keep looping.
return output
```

This matches our existing `remove_dot_segments_step` in
`Parser.Turtle.fst` (lines 154–192). **Keep it.** The v2 plan
**re-homes** the existing function into the new module with
identical semantics; no behaviour change.

### §1.4 Recompose (§5.3)

```
recompose(T):
    result = ""
    if defined(T.scheme):    result ++= T.scheme ++ ":"
    if defined(T.authority): result ++= "//" ++ T.authority
    result ++= T.path
    if defined(T.query):     result ++= "?" ++ T.query
    if defined(T.fragment):  result ++= "#" ++ T.fragment
    return result
```

## §2. Data types

```fstar
noeq type iri_parts = {
  ip_scheme    : option string;    // without trailing ':'
  ip_authority : option string;    // without leading '//'
  ip_path      : string;           // may be ""
  ip_query     : option string;    // without leading '?'
  ip_fragment  : option string;    // without leading '#'
}
```

**All string operations are byte-level via `Parser.FastString`.** No
call site in the new module references `FStar.String.length`,
`FStar.String.sub`, or `FStar.String.index`. This is the single most
important rule for staying inside Z3's budget — every byte-indexed
primitive is O(1) and the solver models them as uninterpreted functions
plus the length refinement.

Per RFC 3986 ABNF, scheme/authority/path/query/fragment characters are
restricted to ASCII (sub-`unreserved`, `reserved`, `pct-encoded`
productions). IRIs (RFC 3987) permit a broader Unicode range inside the
`ipath` / `iquery` / `ifragment` bodies, but:
- our resolver **does not** inspect those bytes; it only scans for the
  ASCII delimiters `:`, `/`, `?`, `#`, `.`;
- non-ASCII bytes are preserved as raw bytes in the output;
- we do **no** Unicode normalisation (stated in §8 below).

This means no codepoint decoding. `fs_cp_at` / `fs_cp_len` are **not
used** in this module.

## §3. Module skeleton

**New file:** `formal/fstar/Parser.IRI.fst`.

**Rationale for factoring out of `Parser.Turtle.fst`:**

- Turtle isn't the only consumer. Once we finish Parser.TriG (already
  done) and the SPARQL prologue BASE handling in
  `SPARQL11.Parser.fst`, and RDF/XML's `xml:base` resolution in
  `Parser.RDFXML.fst`, all four modules will want this resolver.
- Keeping the resolver inside `Parser.Turtle.fst` forced duplicate
  helpers in any module that couldn't transitively `open` Turtle
  (RDF/XML does not open Turtle today).
- A dedicated module also bounds the Z3 workload per verification call:
  we want to be able to tune `--fuel` / `--ifuel` / rlimit on this
  module alone without perturbing the ~3000-line SPARQL algebra or the
  Turtle body.

**LOC budget:**
- `Parser.IRI.fst`: ~350 lines F*.
  - `iri_parts` record + constructors/helpers: ~15
  - `parse_iri` + helpers (ASCII scans for `:`, `//`, `/`, `?`, `#`): ~120
  - `remove_dot_segments` (ported verbatim from `Parser.Turtle.fst`): ~45
  - `merge_paths`: ~15
  - `transform_references`: ~50
  - `recompose`: ~25
  - `resolve_iri_v2` (the top-level): ~10
  - Inline RFC 3986 §5.4 example test table (see §7 below): ~60
    (written as `let _ = assert (resolve_iri_v2 <base> <ref> = <expected>)`
    blocks guarded by `if false then ...` OR as `val _test_N : unit ->
    Lemma (requires True) (ensures ...)` depending on what F* will
    accept — the subagent picks the shape that verifies fastest)

**Entry points (exported `val` signatures, in order):**

```fstar
val parse_iri : string -> option iri_parts

val recompose : iri_parts -> string

val remove_dot_segments : string -> string

val merge_paths : base:iri_parts -> ref_path:string -> string

val transform_references : base:iri_parts -> r:iri_parts -> iri_parts

val resolve_iri_v2 : base:string -> ref_:string -> string
```

`resolve_iri_v2` is the single surface that Turtle's `resolve_iri_hint`
will call:

```fstar
let resolve_iri_v2 base ref_ =
  match parse_iri base with
  | None -> ref_           // caller supplied a malformed base: fall back
                           // to returning the ref unchanged. This matches
                           // Turtle's "relax, pass it through" posture for
                           // bad @base declarations.
  | Some b ->
    match parse_iri ref_ with
    | None -> ref_
    | Some r -> recompose (transform_references b r)
```

**Why a separate `_v2` name:** we do NOT want to touch
`Parser.Turtle.fst` in the module-introduction commit. The commit lands
`Parser.IRI.fst`, verifies + extracts cleanly, and leaves every Turtle
call site untouched (still hitting the in-Turtle `resolve_iri_hint`).
A **separate, second** commit rewires Turtle (see §5). This split keeps
the first commit's blast radius limited to one new file, one
`ocaml-patches.sh` entry (if any — likely none), and one line added to
the `Makefile`'s `FST_FILES` list.

## §4. Termination

For each recursive function, a measure. **No `assume val`, no
`admit`, no `--lax`, no `--admit_smt_queries true`.**

### 4.1 `parse_iri` (non-recursive at top level)

Delegates to four scanners, each of shape:

```fstar
val scan_for_byte :
  s:string ->
  pos:nat{pos <= fs_byte_length s} ->
  byte:nat{byte < 256} ->
  fuel:nat ->
  Tot (r:nat{pos <= r /\ r <= fs_byte_length s}) (decreases fuel)
```

The fuel is bounded at `fs_byte_length s + 1` at the single call site;
each step consumes fuel; the refinement on `r` gives Z3 everything it
needs. This is the exact shape of `find_next_slash`,
`find_query_or_fragment`, and `find_authority_end` already in
`Parser.Turtle.fst` (verified, no `--lax`). Copy the pattern.

`parse_iri`'s top-level logic is straight-line:

1. find first `:` → `colon_pos`. If not found or at position 0,
   ip_scheme = None.
2. if ip_scheme is Some, examine bytes at `colon_pos+1` and
   `colon_pos+2`: if both are `/`, authority starts at `colon_pos+3`,
   runs to the first `/`/`?`/`#` or EOF. Otherwise no authority; path
   starts at `colon_pos+1`.
3. if ip_scheme is None, examine bytes at 0 and 1: if both `/`,
   authority starts at 2 and runs to first `/`/`?`/`#` or EOF.
   Otherwise no authority; path starts at 0.
4. path runs from the current position to first `?` or `#` or EOF.
5. if byte at end-of-path is `?`, query runs from next byte to first
   `#` or EOF. Otherwise ip_query = None.
6. if EOF not yet reached, fragment runs from current+1 to EOF.
   Otherwise ip_fragment = None.

Each step is O(1) slicing after the scans. No recursion at this level.

**Subtlety:** `parse_iri` returns `option iri_parts` to let callers
distinguish a malformed base from a successful parse. The only case
that yields `None` in this planning window is: **none** — this scanner
never fails, because every byte sequence can be parsed as (possibly
empty) scheme + authority + path + query + fragment. If verification
difficulty pushes us there, we can simplify the return type to
`iri_parts` (no `option`). Leave the `option` in the plan and let the
subagent drop it if Z3 is happier without the match on `Some`/`None` at
the call site.

### 4.2 `remove_dot_segments`

The existing `remove_dot_segments_step` in `Parser.Turtle.fst` is our
template. It uses:

```fstar
let rec remove_dot_segments_step
    (input: string) (pos: nat) (out: list string) (fuel: nat)
  : Tot (list string) (decreases fuel)
```

Fuel is bounded at `fs_byte_length path + 2` at the entry call site
(see the existing top-level `remove_dot_segments`). Each iteration
consumes at least one input byte (if there's a non-dot segment) or one
output segment (if it's `./` or `../`). Both are bounded by the byte
length of the input. Fuel = input byte length suffices.

**Do not touch the logic.** Just move it to `Parser.IRI.fst` verbatim.

### 4.3 `merge_paths`, `transform_references`, `recompose`

All non-recursive. `merge_paths` calls `find_last_slash` (already
verified in `Parser.Turtle.fst`). `transform_references` is a
straight-line match on five cases. `recompose` is five conditional
concatenations.

### 4.4 Arithmetic on byte positions — the v1 killer

The v1 attempt tripped Z3 on refinements like
`{pos' = pos + len_of_scheme + 1 /\ pos' <= fs_byte_length s}` when
composing multiple scanners. The fix is:

- **Only the scanners** carry a `{pos <= fs_byte_length s}`
  refinement on their result.
- **Top-level `parse_iri`** does not track position refinements
  in its own return — it computes sub-byte-ranges then uses
  `fs_byte_sub` to extract. `fs_byte_sub` is total (clamps per the
  FastString contract), so a slightly out-of-range `len` just
  returns a shorter string; no refinement burden propagates.
- Avoid `let` bindings that introduce intermediate arithmetic
  with subtraction unless a refinement is already there. If Z3
  balks, introduce a helper with its own explicit refinement — don't
  inline.

If, after a first pass, Z3 is slow but green: fine, commit. If Z3 is
red: the fallback in §4.5.

### 4.5 Fallback if Z3 chokes

1. Push rlimit on the problematic function: `#push-options "--z3rlimit
   50"`. This is already used elsewhere in the codebase.
2. Introduce a helper lemma with an explicit `Lemma` signature for the
   arithmetic obligation.
3. Switch from `nat`-index arithmetic to a `list (nat * nat)` of
   (start, length) byte spans for `parse_iri`'s intermediate
   representation; this lets the `decreases` clause ride on list
   length instead of byte position.
4. **Last resort only:** `decreases %[fuel; input_length]` lexicographic
   measure, if some helper genuinely needs it. Do NOT reach for
   `--admit_smt_queries true` — that flag is what we are trying to
   get away from.

## §5. Call-site migration — separate follow-up commit

After `Parser.IRI.fst` is landed and green:

1. In `Parser.Turtle.fst`, replace the body of `resolve_iri_hint`:

   ```fstar
   let resolve_iri_hint (st: turtle_state) (rel: string) (has_colon: bool)
     : string =
     if fs_byte_length rel = 0 then st.base_iri
     else if has_colon then rel
     else if has_dot_segment rel then
       Parser_IRI.resolve_iri_v2 st.base_iri rel
     else if FStar.Char.int_of_char (fs_byte_index rel 0) = 0x2F then
       // fast path: absolute path, no dots — just splice
       if fs_byte_length st.base_iri = 0 then rel
       else
         let cut = find_last_slash st.base_iri (fs_byte_length st.base_iri) in
         if cut > 0 then String.concat "" [fs_byte_sub st.base_iri 0 cut; rel]
         else String.concat "" [st.base_iri; rel]
     else
       // fast path: simple rel with no dot-segments — no §5.2 machinery
       Parser_IRI.resolve_iri_v2 st.base_iri rel
   ```

   **Rationale:** keep the `has_dot_segment` fast path for the common
   case of a bare local name (`"g"`) against a base that ends in `/`.
   In a profiling pass on N-Triples-style inputs, that path accounts
   for >90% of resolver calls; sending every one of them through the
   full §5.2 machinery would cost a measurable amount on hot parses,
   and the fast path is already correct for that case.

   **Important:** the middle branch (absolute-path reference, no dots)
   takes a shortcut that the v2 resolver would take the long way
   round. Per §5.2.2, an absolute-path ref with a defined base
   should: keep `B.scheme`+`B.authority`, use `remove_dot_segments(R.path)`,
   drop `B.query`, keep `R.query`, keep `R.fragment`. Our fast path
   splices "authority + rel" and skips `remove_dot_segments` because
   `has_dot_segment rel = false` implies there are no dots to remove.
   So it's safe iff `has_dot_segment` is truly precise for this case.
   If v2 exposes a bug there, drop the middle fast path and go
   straight through `resolve_iri_v2`.

2. Leave `resolve_iri` (the in-Turtle function) defined for now, but
   mark it with a `// TODO: retire after Parser.IRI v2 lands` comment.
   A third cleanup commit deletes it once no caller remains.

3. Delete the `resolve_iri` *callers* that aren't part of the hint
   path, if any exist. (Grep the Turtle module; a quick scan of the
   file shows only `resolve_iri_hint` is called externally.)

4. Re-extract, re-patch, run the full RDF + SPARQL W3C test suites.
   Expected delta documented in §6.

## §7. Risks

### 7.1 Query-only and empty-ref corner cases

These are the hardest cases in the §5.2 ladder. The v1 writeup found
six confirmed wrongs in the query-only family alone:
- `s007` `?y`
- `s049` `?y`
- `s259` `?y`
- `s296` `.?a=b` (dot-then-query — the scanner must *not* treat the
  `.` as a path segment before peeling off the query; the RFC's
  definition of "R.path" is what determines this)
- `s299` `..?a=b`
- `s297` / `s300` `.#a=b` / `..#a=b`

The v2 resolver handles these because `parse_iri` decomposes the ref
**before** `transform_references` branches, so `R.path = "."` and
`R.query = "a=b"` fall naturally into the `R.path != "" /\ !starts-with
"/"` branch → merge + `remove_dot_segments` on `R.path` only, and
`T.query = R.query`. No dots leak into the query.

**Subagent must hand-verify these with an in-file assertion table**
(see §7.4 below).

### 7.2 Dot-segment edge cases

RFC 3986 §5.4.1 (normal examples) and §5.4.2 (abnormal examples) list
33 canonical cases. Our `remove_dot_segments_step` is already correct
for these (they're covered by the existing rdf-turtle tests that pass).
The v2 plan does **not** change `remove_dot_segments` — it imports it
unchanged.

### 7.3 RFC 3987 / non-ASCII characters in IRI bodies

Bytes ≥ 0x80 may appear inside authority/path/query/fragment in
real-world files. Per §2 above, we carry them through as opaque bytes.
Since the resolver's byte-level scans only match the ASCII delimiters
`:`, `/`, `?`, `#`, `.`, they will never stop inside a multi-byte
UTF-8 sequence — because UTF-8's continuation bytes (0x80–0xBF) and
lead bytes (0xC2–0xF4) all fall outside our delimiter set. No codepoint
decoding is required.

**Documented limitation:** we do not do Unicode normalisation, case
folding, or IDN ToASCII/ToUnicode. Equal-up-to-NFC IRIs will compare
as distinct. This is not a regression — v1 did not do these either.

### 7.4 Inline test matrix (`assert` block)

Include ~10 examples from RFC 3986 §5.4 in `Parser.IRI.fst` as
`let _ = assert (resolve_iri_v2 b r = expected)` at the bottom of the
file (or equivalent `val / let` lemma shape if F* refuses the
top-level `assert`). Suggested minimum set:

```
base = "http://a/b/c/d;p?q"

("g:h",      "g:h")                     // §5.4.1 normal/abs
("g",        "http://a/b/c/g")          // §5.4.1 normal
("./g",      "http://a/b/c/g")
("g/",       "http://a/b/c/g/")
("/g",       "http://a/g")
("//g",      "http://g")                // the one v1 got wrong
("?y",       "http://a/b/c/d;p?y")      // the one v1 got wrong
("g?y",      "http://a/b/c/g?y")
("#s",       "http://a/b/c/d;p?q#s")
("g#s",      "http://a/b/c/g#s")
("g?y#s",    "http://a/b/c/g?y#s")
(";x",       "http://a/b/c/;x")
("g;x",      "http://a/b/c/g;x")
("g;x?y#s",  "http://a/b/c/g;x?y#s")
("",         "http://a/b/c/d;p?q")      // empty ref
(".",        "http://a/b/c/")
("./",       "http://a/b/c/")
("..",       "http://a/b/")
("../",      "http://a/b/")
("../g",     "http://a/b/g")

("../../g",  "http://a/g")
```

Drop the ones that don't parse as static strings at F* top level; the
list is the reviewer's test of intent, not a live test harness.

### 7.5 Interaction with FastString Pass 2 codepoint primitives

None expected. The codepoint primitives `fs_cp_at` / `fs_cp_len` are
**not called** from `Parser.IRI.fst` (stated in §2). If a future refactor
adds non-ASCII character-class tests inside the IRI grammar (we don't
need any for §5.2), the codepoint layer is available.

### 7.6 Parse-failure behaviour

`parse_iri` is total in practice (every string parses into an
`iri_parts` record, possibly with empty components). The `option`
return is vestigial. If the subagent finds `Some`-wrapping hurts Z3,
drop the `option` from `parse_iri` — no observable behaviour change.

### 7.7 "`%` in path" percent-encoding

The resolver must not decode `%XX` escapes. It must pass them through
byte-for-byte. All of our scans look for single ASCII bytes other than
`%`, so this is automatic — no special handling required. Percent-
encoded triplets live untouched in the path/query/fragment slices.

## §8. Out of scope

Explicitly excluded from this plan:

- **RFC 3987 (IRI) Unicode handling**, including ToASCII/ToUnicode
  for host names (Punycode / IDN).
- **Unicode normalisation** (NFC, NFD, NFKC, NFKD) of IRI components.
- **Percent-encoding normalisation** — e.g. upcasing hex digits,
  decoding `%7E` to `~`.
- **Case folding** of scheme and host names (RFC 3986 §6.2.2.1).
- **Removing default port** and other §6.2.3 scheme-based
  normalisations.
- **Empty-path special cases** beyond what §5.2.2 says explicitly.
- **Base IRI declaration plumbing** in Turtle / TriG / SPARQL
  parsers. `Parser.IRI.resolve_iri_v2` is a drop-in replacement for
  the existing resolver; how and where each parser obtains its base is
  not changed by this work.
- **IRI parsing** for general-purpose use (e.g. extracting the host
  from an IRI for HTTP routing). `parse_iri` here is narrow:
  it parses *well enough for §5.2 to work* on any input, including
  malformed ones.

The follow-up that deletes `Parser.Turtle.resolve_iri` and migrates
RDF/XML + SPARQL to `Parser.IRI.resolve_iri_v2` is a separate commit
(or commits). Not in scope here.
