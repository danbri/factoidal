# constructwhere04 — FROM IRI not resolved against query base

Agent Upsilon, 2026-04-25.

## Symptom

`sparql11/construct/constructwhere04` fails: expected 4 triples, got 0.

Query:
```sparql
PREFIX : <http://example.org/>
CONSTRUCT
FROM <data.ttl>
WHERE { ?s ?p ?o }
```

Manifest entry uses `qt:graphData <data.ttl>` (loaded as a NAMED graph),
no `qt:data`, so `tc.data_files = []`, `tc.named_data_files = [(file:///.../data.ttl, file)]`.

`FROM <data.ttl>` should promote the named graph to default for WHERE eval.

## Root cause

`apply_query_dataset` in `SPARQL11.Algebra.fst:3274` already exists and is
correctly called by `eval_construct_query` at line 3482. Lookup is by IRI
string equality. For the lookup to succeed, the IRI in `DC_Default` must
equal the named-graph key the runner registered (`file:///.../data.ttl`).

But the IRI in `DC_Default` is the unresolved relative `data.ttl`,
because:

1. `parse_select_query` calls `resolve_relative_iri_tokens base ts'` where
   `base` comes from `parse_prologue`. The query has no `BASE` directive,
   so `base = None`, so `resolve_relative_iri_tokens None ts` is a no-op.
2. `parse_skip_from` has a per-token patch via `resolve_tok_iri` (added by
   `ocaml-patches.sh` patch #65), which DOES resolve `i → ri` using the
   global `current_base_iri_ref` set by the runner. The `is_iri ri` check
   passes — but the constructed `DC_Default i` uses the **unresolved**
   `i`, not `ri`. See `ocaml-output/SPARQL11_Parser.ml:5163-5172`.

So the dataset clause stores `data.ttl` (unresolved). `lookup_named_graph`
fails (no key matches `data.ttl`), returns empty graph, default becomes
empty, BGP yields 0 solutions, CONSTRUCT yields 0 triples.

The PNAME branches (`Tok_PNAME pn`, lines 5174-5189) DO use the resolved
`iri`, so a `FROM :foo` form with prefix expansion to absolute IRI works.

## Fix

F*-first: thread the prologue `base` through `parse_skip_from` and resolve
relative IRIs there using `resolve_query_iri`.

- Add `base : option wf_iri` parameter to `parse_skip_from`.
- For `Tok_IRI i` branches (FROM and FROM NAMED), if `not (is_iri i)`,
  resolve via `resolve_query_iri base i`; on success, emit
  `DC_Default abs` / `DC_Named abs`. On failure (no base, still relative)
  emit `DC_Default i` (preserves current behaviour for cases where
  no resolution is possible — same fallback as elsewhere in the parser).
- Update the 4 call sites: line 2495 (SELECT), line 2583 (ASK), line 2629
  (CONSTRUCT shorthand), line 2659 (CONSTRUCT long form). All four already
  have access to the `base` value from `parse_prologue`.

This puts the resolution logic in F*, kept minimal (~15 lines), no patch
change required. Patch #65's `resolve_tok_iri` global-ref fallback still
handles the runtime fallback when no `BASE` directive is present.

Wait — `base` from `parse_prologue` is `None` when query has no BASE.
The runner's `current_base_iri_ref` is what carries the file:// base in
that case. The F* fix above only helps if we ALSO populate `base` from
some source — but `current_base_iri_ref` is OCaml-only.

Revised approach: keep the F* signature change for forward correctness
(once the spec exposes a base-IRI parameter at the query-parse entry
point), but the IMMEDIATE fix that makes the test pass is fixing the
patch to also rename `i → ri` in `DC_Default` / `DC_Named` constructors.
Patch #65 already does this resolution for `PS_IRI`, `PT_IRI`, `PP_IRI`,
etc.; it just missed the dataset-clause constructors. Adding two lines
to the rename list is mechanical and stays within the patch's stated
scope (per-token base-IRI resolution wiring), not new semantic logic.

Decision: extend patch #65 with `DC_Default i)` → `DC_Default ri)` and
`DC_Named i)` → `DC_Named ri)` rewrites. Keep F* spec unchanged for now
(separate PR can plumb base properly through `parse_skip_from`). This
fits rule #10 because resolve_tok_iri itself is already part of patch #65;
we are completing its wiring.
