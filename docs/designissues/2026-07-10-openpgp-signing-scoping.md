# 2026-07-10 — OpenPGP-subset document signing: scoping

## Status

Research + scoping only, answering the owner's question (2026-07-09):
*"how much of basic gpg-style doc signing or checking could we do in
F\* on top of HACL\*?"* Short answer: **the modern-algorithm verify
path in full, the sign path with one entropy `assume val`, and none
of the legacy tail** — and almost all of the new work is codec
(parser/serializer) work, which is this repo's strong suit, not
cryptography.

## What "gpg-style" means here

OpenPGP, RFC 9580 (July 2024, obsoletes RFC 4880): binary packet
framing, ASCII armor, and (for this scoping) **detached signatures**
and **cleartext-signed messages** over arbitrary byte documents.
This is deliberately NOT the encryption half of OpenPGP — signing
and verification only.

Relation to what we already ship: VC Data Integrity
(`eddsa-rdfc-2022`, `VC.DataIntegrity.fst`) signs the *canonicalized
RDF graph* — W3C-native, graph-shaped. OpenPGP adds byte-level
document signing with interop against the gpg/Sequoia/OpenPGP.js
ecosystem. Different artifact class, same crypto primitives.

## Crypto primitives: already in-tree, nothing new to roll

The boundary `assume val`s in `VC.DataIntegrity.fst` (issue #63
family, realised by vendored HACL\* on native and the self-built
HACL\* wasm on Node/browser — see
`skills/node-crypto-haclstar-vc-wasm-build/SKILL.md`):

- `hash_sha256_hex : string -> string`
- `ed25519_secret_to_public : string -> string`
- `ed25519_sign : string -> string -> string`
- `ed25519_verify : string -> string -> string -> bool`

RFC 9580's modern signing algorithms are **Ed25519 (algorithm 27 in
v6, and the v4 EdDSA-legacy algorithm 22)** over SHA-256/SHA-512.
Ed25519 + SHA-256 are exactly what we vendor; SHA-512 is in HACL\*
and would be one more `assume val` of the same shape under the
existing #63 stub if v6 fingerprints/sigs need it. **Zero new
cryptography is written by us** — crypto-policy skill holds.

## The new work is five codecs, all pure F\*

1. **ASCII armor** (RFC 9580 §6): base64 body + CRC-24 checksum +
   `-----BEGIN PGP SIGNATURE-----` framing. Pure string/byte work.
   CRC-24 is a 24-bit CRC with a fixed polynomial — arithmetic, not
   crypto; fine to implement in F\* (it is an integrity check, not a
   security primitive).
2. **Packet grammar** (§4-5): tag+length framing (old and new
   format), then the packet types we need: Signature (tag 2), Public
   Key (tag 6), Public Subkey (tag 14), User ID (tag 13), and for
   cleartext messages the One-Pass Signature (tag 4) + Literal Data
   (tag 11). Same F\*-parser discipline as every other format in this
   repo (iron rule #4).
3. **Signature hashing rules** (§5.2): reconstruct the exact byte
   sequence that gets hashed — document bytes (+ CRLF normalization
   for text-mode/cleartext), hashed subpacket area, and the v4/v6
   trailer. This is the fiddly, test-vector-driven part; it is byte
   assembly, which per iron rule #11 belongs in F\*
   (`serialize : data -> Tot (list u8)`).
4. **MPI / native octet encodings** for key material and signature
   values (§3.2).
5. **Fingerprints & Key IDs** (§5.5.4): v4 = SHA-1 (!), v6 =
   SHA-256. For *verification* we can compute v6 fingerprints with
   existing SHA-256; v4 fingerprints need SHA-1 — HACL\* has SHA-1
   (legacy-marked), one more #63-shaped `assume val`, used for
   identification only, never as a security boundary. Disclose that
   plainly in the module banner.

Cleartext signed messages (§7) add dash-escaping and a `Hash:`
header — trivial on top of the above.

## Slices

**Slice 1 — VERIFY (recommended first): detached + cleartext
verification for Ed25519 keys.**
`gpg --verify`-equivalent for `.sig`/`.asc` files produced by modern
gpg (v4 EdDSA-legacy and v6 Ed25519 signatures). New F\* module
family `OpenPGP.Armor` / `OpenPGP.Packet` / `OpenPGP.Signature`;
zero NEW `assume val` beyond (possibly) SHA-512 and SHA-1-for-
fingerprints under the existing #63 pattern. Test corpus: RFC 9580
test vectors (Appendix A) + a vendored fixture set generated by real
gpg (Ed25519 key, detached sigs over known documents, cleartext
messages) with generation commands recorded in PROVENANCE.md.
Consumer: `factoidal pgp-verify <doc> <sig> <pubkey>` CLI arm +
npm `pgpVerify()`. Size: **M** (the codecs + trailer rules; the
crypto call is one line).

**Slice 2 — SIGN + KEYGEN.** Needs OS entropy: ONE new
`assume val fx_random_bytes : nat -> string` under rule #3 (stub
patch + open issue), realised per-consumer; browser gets
`crypto.getRandomValues`, Node gets `crypto.randomBytes`, native
gets `/dev/urandom` read. Secret keys we generate ourselves are
stored unencrypted or not at all (stdin/env) in slice 2 — S2K
secret-key encryption is explicitly deferred. Interop gate: gpg
verifies our detached signatures. Size: **S** on top of slice 1.

**Explicitly out of scope (and why):**
- RSA PKCS#1 v1.5, DSA, ElGamal — legacy; HACL\* ships RSA-PSS but
  not v1.5 signature padding, and hand-writing v1.5 padding is
  adjacent to rolling our own crypto (crypto-policy skill: don't).
- All encryption (SEIPD, AEAD, S2K) — different feature, different
  risk surface.
- Web-of-trust / keyring management / key servers — protocol+policy,
  parked with the other protocols per the standing goal.
- Compressed-data packets (tag 8) in signed messages — needs a
  DEFLATE implementation; detached/cleartext signatures never
  require it. Reject with a clear error.

## Conformance target (honesty per rule #25)

There is no W3C-style conformance suite for OpenPGP. Measured
targets, dashboard-row shaped:
1. RFC 9580 Appendix A test vectors: N pass / N total (count them
   when vendoring).
2. gpg-interop fixture set (our own, provenance-recorded): X
   verify-pass over Y fixtures, and for slice 2, gpg accepting Z of
   Z signatures we produce.
Both run in a `pgp_runner` (or a `suite_runner` subcommand if #89
lands first).

## Recommendation

Slice 1 is a bounded, honest M-sized win with the same shape as our
best work: verified codecs around an existing verified primitive.
It should wait behind the current ledger burn-down (CSVW, JSON-LD,
XML firming) since it opens a NEW row rather than closing an
existing one — but nothing about it is speculative; every dependency
already exists in-tree.
