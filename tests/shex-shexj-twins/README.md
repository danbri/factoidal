# ShExJ twins for ShExC-only vendored schemas

The shexTest corpus vendored at `third_party/testing/shex/` (submodule pin
`7d0cd92`) ships two of its three "extends" fixture schemas — and one more
introduced alongside them — as ShExC (`.shex`) only, with no matching
ShExJ (`.json`) twin under `third_party/testing/shex/schemas/`. Everywhere
else in the corpus, `bin/shex-runner/shex_runner.ml` consumes the ShExJ
twin (its header documents the "ShExC vs ShExJ" scope cut: 342/346 unique
schemas have one). These 3 schemas are the exception:

| Schema | Fixtures affected |
|---|---|
| `extends-abstract-multi-empty.shex` | 7 (`extends-abstract-multi-empty_*`) |
| `extends-closed-diamond.shex` | 8 (`extends-closed-diamond_*`) |
| `extends-closed-3diamond-split.shex` | 8 (`extends-closed-3diamond-split_*`) |

Checked against upstream shexSpec/shexTest (`git -C third_party/testing/shex
fetch`, master branch as of 2026-07-05): these 3 schemas are ShExC-only
upstream too — there is no newer commit that adds their ShExJ twins. The
gap is real, not a stale pin.

A 4th file, `shapeExtern.shextern.json`, is the same kind of gap but for a
different fixture family: `sht:trait sht:ExternalShape` fixtures
(`shapeExtern_pass`, `shapeExtern_fail`, `shapeExternRef_pass`,
`shapeExternRef_fail`) point `sht:shapeExterns` at
`third_party/testing/shex/schemas/shapeExtern.shextern` — a `.shextern`
fixture that is *always* ShExC (the shexTest corpus defines no ShExJ form
for this extension at all, not just for this one file), one line:
`<http://a.example/Sext> { <http://a.example/p2> . }`. The runner merges
this shape's decoded ShapeDecl into the schema in place of any
`SE_ShapeExternal` placeholder with a matching `sd_id` (see
`bin/shex-runner/shex_runner.ml`'s "shapeExtern-merge" section) — the same
role a real ShEx implementation's out-of-band external-shape resolver
plays.

Per CLAUDE.md rule #2 ("code is extracted, not hand-written") and the
project's discipline against silently patching vendored test inputs,
these twins are **not** written into the submodule and are **not**
generated by running a third-party ShExC-to-ShExJ compiler offline (that
would make an external, unverified tool the source of truth for a
conformance fixture). Instead they are hand-translated here, in a
separate directory, clearly labelled as derived artifacts.

## Translation method

Each `.json` file in this directory is a direct, mechanical translation of
its same-basename `.shex` file, applying the ShExJ encoding conventions
that formal/fstar/ShEx.Schema.fst's decoder already implements — cross-
checked against **real** vendored ShExJ twins elsewhere in
`third_party/testing/shex/schemas/` that exercise the same ShExC
constructs, not invented from the spec text alone:

- `EXTENDS @<Label>` → the enclosing `Shape` object gets an `"extends":
  [<Label IRI>, ...]` array (one entry per `EXTENDS` clause). Confirmed
  against the vendored `0Extends1.json` (single extends, no other
  constraints — flat `{"type":"Shape","extends":[...]}`, no `ShapeAnd`
  wrapper needed) and `Extend3G.json` (multiple `EXTENDS` folded into one
  `"extends"` array, e.g. shape `G`'s `EXTENDS @<E> EXTENDS @<F>` →
  `"extends":["...#E","...#F"]`).
  `extends-abstract-multi-empty.shex`'s `EmployeeShape` and both diamond
  schemas' `BOTTOM` shape use this exact pattern with 2-3 entries.
- `ABSTRACT <Label> { ... }` → the `ShapeDecl` gets `"abstract": true`
  alongside `"id"`/`"shapeExpr"`. Confirmed against `Extend3G.json`'s `A`,
  `B`, `D`, `E` shapes.
- A bareword quoted string in a value set (e.g. `["G0A" "G0B" "G0C"]`) →
  each entry becomes `{"value": "G0A"}` with **no** `"type"` key (plain
  string, not an explicitly-typed literal). Confirmed against the
  vendored `1val1STRING_LITERAL2.json` (`["STRING_LITERAL2"]` → `[{"value":
  "STRING_LITERAL2"}]`) — contrast with `1val1DECIMAL.json`, where a
  numeric bareword literal `[0.0]` gets an explicit `"type":
  "http://www.w3.org/2001/XMLSchema#decimal"`.
- `@<Label>` as a `TripleConstraint`'s value expression → the bare label
  IRI string (`"valueExpr": "http://a.example/PersonShape"`), matching
  `decode_shape_expr`'s `JString s -> SE_Ref s` case and every vendored
  twin that references another shape by name.
- `xsd:string` / `IRI` node constraints → `{"type":"NodeConstraint",
  "datatype": "http://www.w3.org/2001/XMLSchema#string"}` /
  `{"type":"NodeConstraint","nodeKind":"iri"}` (lowercase `"iri"` per
  `ShEx.Schema.fst`'s `decode_node_kind`).
- `;`-separated statements inside `{ }` → `"type":"EachOf"` with an
  `"expressions"` array; `|`-separated alternatives inside `( )` →
  `"type":"OneOf"`. A single statement needs no wrapper.
  `extends-abstract-multi-empty.shex`'s `PersonShape` uses both, nested
  (`EachOf[ OneOf[ TripleConstraint, EachOf[...] ], TripleConstraint ]`).
- Cardinality: `+` → `"min":1,"max":-1`; `?` → `"min":0,"max":1`; the
  ShExJ default (`min:1,max:1`, omittable) needs no explicit fields.
- An empty `{}` shape body (as in `EmployeeShape`, which is pure
  `EXTENDS` with no local triple expression) → the `Shape` object simply
  omits the `"expression"` key entirely (confirmed against `0Extends1.json`'s
  `S2`), matching `decode_shape`'s `json_get_field "expression"` returning
  `None` for "not present" rather than an empty object.

Every predicate/shape IRI was checked against the fixture's own `BASE`
declaration and against the corresponding `validation/*.ttl` data files
(e.g. `extends-closed-diamond.ttl`'s `<p>` values `"G0A"`/`"G0-0A"`/…
literally match this twin's `NodeConstraint` value sets) and the
manifest's `sht:focus`/`sht:shape` fields, so the translation is
verifiable independent of trusting the translator's ShExC reading.

## Per-file provenance

Each `.json` file also carries a top-level `"_provenance"` string field
naming its source `.shex` file. This is not part of the ShExJ grammar —
`ShEx.Schema.fst`'s decoder reads named fields via `json_get_field` and
ignores unrecognised keys, so the extra field is inert at validation
time and exists purely as an in-band provenance note (JSON has no
comment syntax).

## Runner integration

`bin/shex-runner/shex_runner.ml`'s `json_twin_of_schema_path` first looks
for the ShExJ twin under `third_party/testing/shex/schemas/` (the
submodule); if absent, it falls back to this directory
(`tests/shex-shexj-twins/<basename>.json`) before giving up and emitting
a SKIP. Only these 3 files exist here — every other schema in the corpus
still resolves inside the submodule.

## Expected outcomes

These are `sht:trait sht:Extends` fixtures — Stage 6 territory per
`ShEx.Validation.fst`'s header. As of this writing the sibling agent's
`extends` semantics were not yet landed in `ShEx.Validation.fst`, so
`ShEx_Validation.validate_focus` is expected to return `None` (DEFERRED)
for all 23 fixtures once the schema decodes successfully — the point of
this twin set is to get these fixtures off the SKIP bucket (schema now
decodes) and onto an honest DEFERRED/PASS/MISMATCH verdict once
`ShEx_Validation.ml` actually implements `extends`/`abstract`, not to
force a PASS.
