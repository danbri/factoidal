# tests/did — did:key resolution vectors

Fixtures for `bin/did-runner/did_runner.ml`, which calls the F\*-extracted
`DID_Key.did_key_document` (from `formal/fstar/DID.Key.fst`) and checks its
output against these hand-transcribed expected DID Documents.

The vendored `third_party/testing/did` submodule
(w3c/did-test-suite) is a mocha conformance harness whose did:key suite
drives a *live HTTP resolver endpoint per implementation*
(`packages/did-core-test-server/suites/implementations/*.json` — each file
lists a `didMethod`, an `implementation` URL, and per-DID expected
properties, but there is no offline "resolve this string, get this
document" fixture format). It has no clean did:key resolution vectors this
runner can execute directly, so the expected documents below come from the
did:key spec's own text instead, per the task's stated fallback.

## Layout

Each vector is a pair of files sharing a basename:

- `<name>.did` — the `did:key:z...` identifier, one line.
- `<name>.nt`  — the expected DID Document as N-Triples (`#`-prefixed
  comment lines and blank lines are ignored by the runner; triple lines
  must match `RDF.NQuads.Serialize.nq_line_for_triple_default_graph`'s
  exact output format, since the runner compares sorted line sets, not a
  semantic RDF equivalence).

## Vectors and their sources

1. `spec-canonical-z6MkhaXg` — the w3c-ccg `did-method-key` spec's
   "Create" section canonical example
   (`did:key:z6MkhaXgBZDvotDkL5257faiztiGiC2QtKLGpbnnEGta2doK`), full
   document transcribed verbatim (`keyAgreement` dropped — deferred, see
   `DID.Key.fst`'s banner). Source: [w3c-ccg/did-method-key, 2022-11-17
   snapshot](https://web.archive.org/web/20221117145136/https://w3c-ccg.github.io/did-method-key/).
   The live spec has since moved to a `Multikey`/`did/v1.1` revision; this
   module targets the `Ed25519VerificationKey2020` revision, matching what
   `VC.DataIntegrity.fst`'s `eddsa-rdfc-2022` proof pairs with in practice.

2. `spec-test-vectors-z6MkiTBz` — the same spec's "Test Vectors" section,
   "Multicodec Example"
   (`did:key:z6MkiTBz1ymuepAQ4HEHYSF1H8quG5GLVVQR3djdX3mDooWp`). That
   section gives only the `verificationMethod` array verbatim; the other
   four triples are assembled by hand-applying the spec's own normative
   "Document Creation Algorithm" text (same page, steps 5-7: each of
   `authentication`/`assertionMethod`/`capabilityInvocation`/
   `capabilityDelegation` is initialized to an array holding exactly the
   verification method's `id`) — not generated by `DID.Key.fst`.

3. `vendored-spruce-z6MkpTHR` — the key vendored by
   `third_party/testing/did`'s `did-key-spruce.json` fixture
   (`did:key:z6MkpTHR8VNsBxYAAWHut2Geadd9jSwuBV8xRoAnwWsdvktH`). That
   vendored JSON encodes the key as `Ed25519VerificationKey2018` +
   `publicKeyJwk`, a different cryptosuite than this module targets, so
   its document isn't directly reusable; the expected document here is
   assembled the same way as vector 2 (spec template, substituted DID).
   The underlying key bytes were cross-checked independently: base58
   multibase-decoding `z6MkpTHR8VNsBxYAAWHut2Geadd9jSwuBV8xRoAnwWsdvktH`
   and stripping the `0xed01` multicodec prefix yields the same 32 bytes
   as base64url-decoding the vendored fixture's `publicKeyJwk.x`.

Predicate/type IRIs (`https://w3id.org/security#verificationMethod`,
`#controller`, `#authenticationMethod`, `#assertionMethod`,
`#capabilityInvocationMethod`, `#capabilityDelegationMethod`,
`#Ed25519VerificationKey2020`, `#publicKeyMultibase`, `#multibase`) are the
exact `@id`/`@type` mappings fetched from
`https://www.w3.org/ns/did/v1` and
`https://w3id.org/security/suites/ed25519-2020/v1`, not re-derived.
